# cpu_user

[English version](../en/stat.cpu_user.md)

---

## これは何？

`cpu_user` は、CPUが**ユーザー空間**のコードを実行した時間の割合です。アプリケーション、データベース、言語ランタイムなど、カーネル以外のすべての処理がここに計上されます。Linuxカーネルは `/proc/stat` にCPUごとのティックカウンターとして記録しており、syslenzはサンプリング間隔の割合として公開します。

レストランの厨房に例えるなら、CPUがシェフです。`cpu_user` はシェフが実際に料理をしている（アプリが動いている）時間。`cpu_system` はカーネルが食材補充などの管理業務に費やす時間。`cpu_iowait` はシェフが配達待ちで手が空いている時間です。

```
  CPU時間の内訳 (100%)
  ┌──────────────────────────────┐
  │ user   ████████████ 60%      │  <- あなたのアプリが動く場所
  │ system ████ 20%              │  <- カーネルがアプリの代わりに動く
  │ iowait ██ 10%                │  <- CPUはアイドル、I/O待ち
  │ idle   ██ 10%                │  <- 仕事がない
  └──────────────────────────────┘
```

---

## なぜ重要？

`cpu_user` が高いということは、アプリケーションが実際に計算をしているということです。これは多くの場合**健全なサイン**です。CPUが生産的に動いている証拠です。しかし、プロセスの暴走、アルゴリズムの非効率、またはハードウェアが処理しきれないほど負荷が増えたサインでもあります。

重要なポイント：**`cpu_user` が高いだけでは問題ではありません。** 問題なのは：
- `cpu_user` が高く、かつレイテンシが上昇している（CPUがボトルネック）
- `cpu_user` が高く、かつ `cpu_iowait` も高い（CPUは忙しそうに見えるが実は待っているだけ、本当の問題はI/O）
- 特定のプロセスが予期しないほどCPUを食いつぶしている（暴走）

シナリオ：普段5分で終わるバッチジョブが40分かかるようになった。`cpu_user` は95%に張り付いている。CPUが遅いのか？それとも誰かがフルテーブルスキャンするSQL文をプッシュしたのか？この指標はユーザー空間を指し示す。調査はそこから始まる。

## 読み方

```sh
# リアルタイムCPU内訳、1秒サンプリング
mpstat -P ALL 1

# ユーザーCPUを消費しているプロセスは？
top -b -n 1 | head -20

# より詳細に
pidstat -u 1 5
```

| `cpu_user` の値 | 解釈 |
|----------------|------|
| 0〜30% | 十分な余裕あり |
| 30〜70% | 忙しいシステムの通常負荷 |
| 70〜90% | レイテンシへの影響を監視、トレンド確認 |
| 90〜100% | CPUバウンド。スケールアップまたは最適化が必要 |

**セットで見るべき指標：**
- `cpu_system`：systemも高い場合、アプリが多くのシスコールを発行 → ファイルI/O、ネットワークを確認
- `cpu_iowait`：iowaitが高くuserも高い場合、userは誤解を招く → 本当のボトルネックはストレージ
- `stat.procs_running`：runqueueが増えているならCPUが本当に飽和している

## 実際のエピソード

動画トランスコードサービスが数ヶ月間、`cpu_user` 60%で快適に動いていた。ライブラリのアップグレード後、ユーザーからジョブが3倍遅くなったと報告が届いた。モニタリングを見ると `cpu_user` が98%に跳ね上がっていた。チームの最初の反応は「サーバーを増やさなければ」だった。

しかし `pidstat` で詳しく見ると、1つのトランスコードワーカーが1CPUコアの95%を使い、残り15のワーカーはほぼアイドル状態だった。アップグレードしたライブラリが、無言でマルチスレッドからシングルスレッドモードに変わっていたのだ。仕事が1スレッドに集中していた。

修正：スレッドを再有効化する設定を1行書いた。`cpu_user` は98%から65%に下がり、全コアに分散した。新しいハードウェアは不要だった。

**教訓：** `cpu_user` はCPUが「頑張っている」ことを示す。どこで、どれだけ効率的に頑張っているかは示さない。どのプロセス・スレッドが動いているか、必ず掘り下げること。

## 高い時にやること

**ステップ1：誰がCPUを使っているか特定する。**
```sh
# CPU消費上位のプロセス
ps aux --sort=-%cpu | head -15

# スレッド単位の内訳
pidstat -u -t 1 5
```

**ステップ2：実際に問題を引き起こしているか確認する。**
レイテンシは上昇しているか？リクエストはタイムアウトしているか？バッチワークロードでユーザー影響がないなら、高い `cpu_user` は問題ない。APIサーバーで95%なら、リクエストがキューに溜まっている可能性がある。

**ステップ3：iowaitによる偽装を排除する。**
```sh
# iowaitも高い場合、問題はストレージであって計算ではない
cat /proc/stat | awk 'NR==1{print "user="$2, "system="$4, "iowait="$6, "idle="$5}'
```

**ステップ4：ホットなプロセスをプロファイルする。**
```sh
# 実行中のコードをサンプリング（perfが必要）
perf top -p <PID>

# あるいはstraceでどのシスコールが支配的か確認
strace -c -p <PID>
```

**ステップ5：CPUが本当に飽和しているなら**：
- 水平スケール（インスタンス追加）
- アルゴリズム最適化（まずプロファイルから）
- リクエストあたりの仕事量を減らす（キャッシュ、バッチ処理）
- NUMAシステムではCPUアフィニティのチューニング

## よくある間違い

**cpu_user 90%を自動的に悪いと判断する。** 動画エンコーダが90%なら健全だ。それがエンコーダの仕事。通常のトラフィック下でWebAPIが90%なら警告サインだ。

**iowaitとセットで見ない。** `cpu_user + cpu_iowait = 95%` なら、CPUは忙しそうに見えるが実はほとんどディスク待ちだ。計算リソースを増やしても解決しない。

**単発スパイクに反応する。** 持続的なトレンドを見ること。ガベージコレクション中の5秒間の100%スパイクは正常。通常トラフィック下で10分以上90%超が続くのは異常だ。

**コアごとのビューを見落とす。** システム全体の `cpu_user` は全コアの平均だ。15コアがアイドルの状態で1コアが100%だと、集計値はわずか6%にしか見えない。必ずCPUごとのデータを確認すること。

## 関連項目

- `stat.cpu_iowait` — I/O待ちのCPUアイドル時間。cpu_userと並んで最も誤読されやすい指標
- `stat.cpu_system` — カーネル実行時間。systemが高い場合、ユーザーコードからのシスコールが多い
- `stat.procs_running` — ランキュー長。CPUがボトルネックのとき増える
- `schedstat.cpu_stats` — より深い分析のためのCPUごとのスケジューラ統計
