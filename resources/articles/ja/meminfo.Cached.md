# Cached

[English version](../en/meminfo.Cached.md)

---

## これは何？

`Cached` は、ディスクから読み書きされたファイルのページキャッシュとして使われているRAMの量です。アプリケーションがファイルを開くと、カーネルはそれをRAMに読み込んで保持します。次回同じファイルを誰かが読むときはディスクアクセスが不要で、データはRAMから直接来ます。

カーネルによる自動ディスク高速化と思えばよいでしょう。アプリケーションの関与なしに、カーネルが何をキャッシュして何を追い出すかを決めます。メモリ圧力が上がると、キャッシュページが最初に回収されます——ディスク上にデータが存在する「クリーン」なコピーなので、破棄してもコストはかかりません（将来のディスク読み取りが増えるだけです）。

```
  初回読み取り：ファイル → ディスクI/O → ページキャッシュ → アプリ
  2回目以降：ファイル → ページキャッシュ → アプリ （ディスクなし！）

  メモリが必要になった時：
  ページキャッシュのページ → 追い出し → MemFree増加 → アプリにRAM提供
  （データはディスクに残るので何も失われない）
```

---

## なぜ重要？

**大きな `Cached` は通常良いことです。** `Cached` が50 GBのDBサーバーは、ワーキングセットをディスクではなくRAMから読んでいます。読み取りレイテンシはミリ秒ではなくマイクロ秒。この50 GBは「無駄」ではありません——仕事をしています。

**`Cached` が突然減るのは悪いことです。** 別のワークロードがメモリを必要とし、カーネルがキャッシュを追い出すと、次の読み取りは遅いディスクI/Oになります。これが「コールドスタート」効果です：サブミリ秒レイテンシで動いていたサービスが、ワーキングセットが再読み込みされるまで1回の操作に50〜200msかかるようになります。

**認識すべき典型的なパターン：**

| `Cached` の挙動 | 意味 |
|----------------|------|
| 大きく安定 | 良好——ワーキングセットが温まっている |
| 大きく減少中 | メモリ圧力——他の何かがRAMを要求している |
| 小さく増加中 | 再起動後のウォームアップ中 |
| ほぼゼロ | キャッシュが追い出された——温まるまでI/Oが遅い |

## 読み方

```sh
# キャッシュサイズを利用可能量と一緒に確認
grep -E "MemTotal|MemAvailable|Cached|Buffers" /proc/meminfo

# キャッシュと利用可能量を一緒に監視
watch -n 2 'grep -E "MemAvailable|Cached:" /proc/meminfo'

# ディスクとキャッシュのどちらから読まれているか
# （pgpgin はディスクから読んだページ数）
grep pgpgin /proc/vmstat
```

**データベースサーバーでは**、キャッシュヒット率対総読み取りの比率が重要指標です。`Cached` が大きくDBが高いバッファヒット率を報告しているなら、良い状態です。

**目安**：単一ワークロード専用サーバーでは、`Cached` が総RAMの60〜80%を使うのは健全です。`MemAvailable` が低下している場合にだけ心配してください。

## 実際のエピソード

ある会社がElasticsearchクラスターを運用していました。各ノードは32 GB RAM。何ヶ月もクエリは平均10ms未満で動いていました。そこに同じノードで動く新しいログ取り込みパイプラインを追加しました。

取り込みパイプラインは数GBのログファイルを書き込みました。カーネルはそれをキャッシュし始め、ElasticsearchのインデックスページをキャッシュからじわじわRと追い出しました。2日かけて、`Cached` の中身はElasticsearchのインデックスからログファイルへと入れ替わりました。クエリレイテンシは10msから400msへ上昇。クラッシュなし、OOMなし——静かで緩やかなパフォーマンス劣化でした。

解決策はワークロードを別ノードに分離することでした。しかし診断するには、キャッシュが中立ではないことを理解する必要がありました——キャッシュには中身があり、その中身が重要なのです。

教訓：データベースや検索サービスのレイテンシが謎めいた上昇を見せたら、何か別のものがキャッシュを追い出していないか確認してください。`/proc/meminfo` の `Cached` はサイズを教えてくれますが、`fincore` や `vmtouch` で実際に何がキャッシュされているかを見ることができます。

## キャッシュが突然減った時にやること

**ステップ1：代わりに何がメモリを消費しているか特定する。**
```sh
# AnonPages を確認——アプリがRAMをより多く消費しているか？
grep AnonPages /proc/meminfo

# RSS上位の消費者
ps aux --sort=-%mem | head -10
```

**ステップ2：I/Oレイテンシが上昇しているか確認する。**
```sh
iostat -x 1 5
# %util と await 列を見る——ディスクが忙しいか？
```

**ステップ3：何がキャッシュされていたか特定する。**
特定のファイルのキャッシュが追い出されたと疑う場合、`fincore` で確認できます：
```sh
# インストール: apt install libfincore / fincore <ファイル名>
fincore /var/lib/postgresql/data/base/...
```

**ステップ4：ワークロード競合が原因なら**、cgroupのメモリ制限で重要サービスのキャッシュを確保するか、ワークロードを別ホストに分離することを検討してください。

## よくある間違い

**「メモリを空けるため」にキャッシュを解放しようとする。** カーネルはメモリが必要な時に自動的にこれを行います。手動でキャッシュを解放する（`drop_caches`）のは不要なキャッシュミスを引き起こすだけです。

**`Cached` と `Buffers` を混同する。** `Cached` はファイルの内容のためのページキャッシュです。`Buffers` はブロックデバイスのメタデータ（ファイルシステムの構造情報であってファイルの中身ではない）です。挙動の異なる別々のプールです。

**コールドキャッシュをクラッシュと間違える。** サーバー再起動後、`Cached` はほぼゼロから始まります。キャッシュが温まるまでサービスは遅くなります。これは正常であってバグではありません。

**パフォーマンスシグナルとしてのキャッシュを無視する。** データベースサーバーで `Cached` が低下しているのは早期警戒です。レイテンシが急上昇するまで待たず、`Cached` のトレンドを時系列で監視してください。

## 関連項目

- `meminfo.MemAvailable` — 実際のメモリ余力（回収可能なキャッシュを含む）
- `meminfo.Buffers` — ブロックデバイスのメタデータキャッシュ（ファイルキャッシュとは別）
- `meminfo.AnonPages` — 回収不可能なアプリケーションメモリ
- `meminfo.MemFree` — 純粋な空きメモリ（通常は誤解を招く指標）
- `vmstat.pgpgin` / `pgpgout` — ディスクから読み書きされたページ数（キャッシュミス率の代替指標）
