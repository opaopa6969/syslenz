# uptime

[English version](../en/uptime.uptime.md)

---

## これは何？

`uptime` は、最後に起動してからシステムが動いている秒数です。`/proc/uptime` ファイルの最初の数字がこれにあたります。読むのは簡単、誤読も簡単。

最後の誕生日（再起動）からのシステムの年齢と考えてください。uptimeが86,400秒のサーバーは1日目。31,536,000秒なら再起動なしで1年稼働していることになります。

```
  /proc/uptime の例：
  1234567.89  4987654.32
  ^            ^
  │            └─ 全CPUのアイドル時間合計（秒）
  └─ 稼働時間（秒）（syslenz が報告する値）

  1,234,567 秒 = 約14.3日
```

---

## なぜ重要？

**予期しない再起動の検出。** uptimeが突然小さい値にリセットされたら、システムが再起動したことになります。これは計画的なもの（カーネル更新）かもしれないし、偶発的なもの（電源障害、OOMキルの連鎖）かもしれないし、悪意のあるもの（誰かが午前3時にデータベースサーバーを再起動した）かもしれません。uptimeの監視は異常検知のトリップワイヤーになります。

**未適用のパッチ。** 400日以上稼働しているサーバーは、ほぼ確実にカーネルセキュリティパッチを見逃しています。Linuxはカーネル更新の適用に再起動が必要です。高いuptimeは「システムが安定している！」に聞こえますが、多くの場合「既知のCVEがある2022年のカーネルで動いている」を意味します。

**安定性のシグナル。** 何度も再起動を繰り返す（数時間ごとにuptimeがリセットされる）サーバーには深刻な問題があります。カーネルパニック、ハードウェア障害、またはクラッシュループが疑われます。本番サーバーのuptimeが低い場合は即刻調査が必要です。

```
  健全性シグナルとしてのuptime：

  新しいシステム：[1日]          <- デプロイ直後として正常
  健全：          [7〜90日]      <- 定期的にパッチ適用
  パッチ負債：    [180日超]      <- セキュリティリスク
  クラッシュループ：繰り返しリセット <- 重大
```

## 読み方

```sh
# 人間が読みやすい形式
uptime
# 例：14:32:01 up 14 days, 3:17,  2 users,  load average: 0.52, 0.58, 0.61

# /proc/uptime から生の秒数
awk '{print $1}' /proc/uptime

# システムはいつ起動したか？
who -b
# または
last reboot | head -3
```

| uptime | 解釈 |
|--------|------|
| 1時間未満 | 直後の再起動 — 意図的かどうか確認 |
| 1〜7日 | 最近のデプロイまたはパッチサイクル |
| 7〜90日 | パッチ適用システムの通常稼働範囲 |
| 90〜180日 | パッチ状況を確認し、メンテナンス窓を計画 |
| 180日超 | セキュリティ負債の可能性。カーネルパッチが未適用 |
| 繰り返しリセット | クラッシュループまたは不安定 — 即刻調査 |

**再起動が予定通りだったか確認：**
```sh
# ログにスケジュールされたメンテナンスがあったか？
journalctl -b -1 | head -20   # 前回起動の最後のメッセージ
last reboot                    # 再起動履歴
```

## 実際のエピソード

あるフィンテックスタートアップの決済処理サービスが270日間問題なく動いていた。チームはその安定性を誇りにしていた。そこへセキュリティ監査が入り、サーバーが8ヶ月前にパッチが出ていたローカル権限昇格のCVEを持つカーネルバージョンで動いていることが判明した。

チームは「システムが安定していたし、何かを壊したくなかった」という理由で自動カーネルパッチを設定していなかった。270日のuptimeは誇りの証だったが、それがリスクになっていた。

さらに悪いことに、ようやくパッチ適用の窓を計画した時、システムが新しいカーネルで廃止予定の機能を使っていることがわかった。パッチで破壊的変更が生じた。「安定していた」システムは9ヶ月分の隠れた技術的負債を積み上げていたのだ。

**教訓：** 高いuptimeは健全なuptimeとは違う。uptimeを最大化するためではなく、予期しない低下を検出し、セキュリティパッチのための最大値の上限を守るために監視すること。

## 予期せずリセットした時にやること

**ステップ1：再起動を確認する。**
```sh
last reboot | head -5
who -b
```

**ステップ2：原因を探る。**
```sh
# 前回起動のカーネルメッセージを確認
journalctl -b -1 -p err | tail -50

# カーネルパニックだったか？
journalctl -b -1 | grep -i "panic\|oops\|BUG\|killed"

# OOMキルだったか？
journalctl -b -1 | grep "oom\|Out of memory"

# ハードウェアエラーを確認
dmesg | grep -iE "hardware error|mce|edac"
```

**ステップ3：意図的な原因を確認する。**
```sh
# スケジュール済みの再起動（systemd）
systemctl list-timers | grep reboot

# カーネル更新が保留中だったか？
needs-restarting -r   # （RHEL/CentOS）
```

**uptimeが高すぎる（パッチ負債）時にやること：**
```sh
# 現在のカーネルバージョンを確認
uname -r

# 利用可能な更新を確認（Debian/Ubuntu）
apt list --upgradable | grep linux-image

# CVEを確認（RHEL/CentOS）
yum updateinfo list security | grep kernel
```

## よくある間違い

**uptimeを最大化することを目標にする。** 「稼働999日！」はLinuxサーバーの成功指標ではない。大抵は未パッチのCVEを意味する。最大uptime方針を設けること：「カーネルパッチがリリースされたら30日以内に再起動する」。

**予期しない再起動にアラートを設定しない。** 深夜3時に予告なく再起動したサーバーはカーネルパニックを起こしていたかもしれない。uptimeリセットへのアラートがないと、何日も気づかない可能性がある。

**uptimeと信頼性を混同する。** サーバーは365日稼働しながら、ディスクが少しずつ埋まり、メモリがリークし、接続が積み上がりながら静かに劣化することができる。uptimeは再起動していないことは示すが、健全であることは示さない。

**アイドル時間フィールドを無視する。** `/proc/uptime` の2番目の数字は全CPUのアイドル時間合計だ。4コアマシンでuptime 1000秒の時、アイドル時間が3800秒なら平均してCPUは95%アイドルだったことになる。ロードアベレージとの健全性チェックに使える。

## 関連項目

- `uptime.idle` — 同ファイルのCPUアイドル時間合計。ロードアベレージの健全性確認に使える
- `stat.procs_running` — 再起動後に高い場合、何かが正常に起動していない
- `loadavg` — 1/5/15分のロードアベレージ。これも再起動でリセットされる
- `journalctl -b -1` — 前回起動セッションのログ。再起動の根本原因分析に使う
