# pgfault

[English version](../en/vmstat.pgfault.md)

---

## これは何？

`pgfault` は**ページフォルト**の総数を計上します。プロセスが仮想メモリのアドレスにアクセスしようとした時、まだ物理メモリのページがマッピングされていない場合に発生するイベントです。カーネルがこれを捕まえ、ページをマッピングし、プロセスを続行させます。

ほとんどのページフォルトは**マイナーフォルト**です。ページはすでにRAMにあり（ページキャッシュや共有メモリなど）、カーネルはそれを指すようにプロセスのページテーブルを更新するだけでよいのです。これは速い — マイクロ秒オーダーです。

`/proc/vmstat` のカウントは起動後の累積値です。重要なのは絶対値ではなく**変化率**です。

```
  プロセスがアドレス 0xABCD1234 にアクセス
           │
           v
  ┌──────────────────┐
  │  ページテーブル: ? │  <- まだマッピングなし → ページフォルト
  └──────────────────┘
           │
           ├─ ページがRAMにある（ページキャッシュ、共有）？  → マイナーフォルト：マッピングするだけ
           │
           └─ ページがRAMにない？                          → メジャーフォルト：ディスクから読む
```

マイナーフォルトはデスクの上にすでにある本を手に取るようなもの。メジャーフォルトは図書館まで本を取りに行くようなものです。

---

## なぜ重要？

適度な `pgfault`（マイナーフォルト）の発生率は完全に正常です。プロセスがメモリを確保して初めてページに触れる時、共有ライブラリに初めてアクセスする時、fork後にコピーオンライトページを継承する時、すべてマイナーフォルトが発生します。忙しいシステムでは毎秒数万件は珍しくありません。

**注意が必要な時：**

- **デプロイ後にレートが急増する** — 新しいコードが異なるメモリアクセスパターンを持ち、マイナーフォルトが増えることがある。通常は問題ないが記録に値する。
- **高いレートが持続し、cpu_systemも高い** — マイナーフォルト処理はカーネルコンテキストで実行される。非常に高いフォルトレートは積み上がって意味のあるカーネルCPUオーバーヘッドになる。
- **作業量の増加なしに pgfault が上昇** — メモリフラグメンテーション、非効率なメモリ割り当て、またはリークによりプロセスが常に新しいページを割り当てマッピングしている可能性がある。

姉妹指標の `pgmajfault`（メジャーフォルト）に深刻なパフォーマンス問題が潜んでいることが多い。常に両方を合わせて確認すること。

## 読み方

```sh
# システム全体の毎秒ページフォルトレート
vmstat 1 | awk '{print $10, $11}'   # カラム：マイナー、メジャーフォルト

# プロセスごとのページフォルトレート
pidstat -f 1 5
# または
/usr/bin/time -v <コマンド>   # 完了後にメジャー+マイナーフォルトを表示
```

| `pgfault` レート（毎秒） | 解釈 |
|------------------------|------|
| 0〜10,000/秒 | 正常。軽いワークロード |
| 10,000〜100,000/秒 | アクティブなワークロード下で正常 |
| 100,000〜500,000/秒 | 重い。メモリ圧力を確認 |
| 500,000/秒超 | 非常に高い。プロセスのメモリパターンを調査 |

**`pgmajfault` との比較：**
- pgfault が50,000/秒でpgmajfaultが5/秒 → 正常なマイナーフォルト活動
- pgfault が50,000/秒でpgmajfaultが2,000/秒 → ページフォルトからの重大なディスクI/O

## 実際のエピソード

検索サービスが夜間の再インデックスジョブを実行していた。エンジニアたちはジョブ中に `cpu_system` が40%に急上昇することに気づいた。通常クエリ時の5%と比べて非常に高い。アプリケーションCPU（`cpu_user`）は正常だった。カーネルは何をしていたのか？

ジョブ中に `pidstat -f 1` を実行すると：
```
PID  minflt/s  majflt/s
1842  87,000      1.2
```

インデクサーから毎秒87,000件のマイナーフォルト。ジョブは大きなバッファを繰り返し確保し、短時間使用して解放し、再確保していた。新しいページマッピングの絶え間ないサイクルが生じていた。修正はスタートアップ時にプールを事前確保して再利用すること。マイナーフォルトは3,000/秒に減少し、`cpu_system` は8%に低下した。

**教訓：** マイナーフォルトは個々は安価だがスケールすると高コストになる。毎秒80,000件のマイナーフォルトを発生させるプロセスは、毎秒80,000回のカーネルトラップ&リターンサイクルを実行している。レイテンシに敏感なシステムでは積み上がる。

## レートが高い時にやること

**ステップ1：どのプロセスがフォルトを発生させているか特定する。**
```sh
pidstat -f 1 5
# minflt/s = マイナーフォルトレート、majflt/s = メジャーフォルトレート
```

**ステップ2：実際に問題を引き起こしているか確認する。**
`cpu_system` を確認する。カーネルCPUが高い場合、フォルト処理のオーバーヘッドが原因かもしれない。アプリケーションのレイテンシも確認。

**ステップ3：メジャーフォルトも高い場合、そちらが優先。**
`vmstat.pgmajfault` を参照 — メジャーフォルトはディスクI/Oを必要とし、桁違いに高コストだ。

**ステップ4：マイナーフォルトレートを下げる。**
```sh
# ページテーブルのオーバーヘッドを下げるためにhugeページを使う（アプリが対応している場合）
echo madvise > /sys/kernel/mm/transparent_hugepage/enabled

# プロセスが頻繁にmmapを使っているか確認
strace -e mmap,mprotect -p <PID> 2>&1 | head -30
```

## よくある間違い

**累積値とレートを混同する。** `/proc/vmstat` は起動後の総数を示す。数週間の稼働後に大きな数字が出るのは当然だ。常に**変化率**を見ること（`vmstat 1` や `pidstat` を使う）。

**メジャーフォルトを確認する前にマイナーフォルトを心配する。** メジャーフォルトはディスクI/Oを含み、マイナーフォルトより約1000倍高コストだ。`pgmajfault` が上昇しているなら、それが緊急問題だ。

**cpu_systemと相関させない。** ページフォルト処理はカーネル空間で実行される。非常に高いマイナーフォルトレートは `cpu_system` の上昇として現れる。`cpu_system` が高く明らかなシスコール活動が見えない場合、フォルトレートを確認すること。

## 関連項目

- `vmstat.pgmajfault` — メジャーページフォルト。ディスクからの読み込みが必要な高コスト版
- `vmstat.pswpin` — スワップから読み込まれたページ。メジャーフォルトの主要な発生源
- `stat.cpu_system` — カーネルCPU時間。高いフォルトレートで上昇する
- `pressure/memory_some_avg10` — メモリ圧力がタスクの遅延を引き起こしているか確認
