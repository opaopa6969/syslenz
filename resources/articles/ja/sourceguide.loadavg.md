## What is this source? / このソースとは？

`/proc/loadavg` はシステムのロードアベレージを公開します。カーネルが5秒ごとに更新する1行5フィールドのファイルです。

```
$ cat /proc/loadavg
2.34 1.87 1.52 3/412 29518
 │    │    │   │  │    │
 │    │    │   │  │    └─ 最後に生成されたPID
 │    │    │   │  └─ システム全体のスレッド総数
 │    │    │   └─ 現在の実行可能/実行中スレッド数
 │    │    └─ 15分ロードアベレージ
 │    └─ 5分ロードアベレージ
 └─ 1分ロードアベレージ
```

ロードアベレージは**指数移動平均**です。ランキュー内（実行中または実行待ち）のスレッド数と、割り込み不可スリープ中のスレッド数を足したものを対象に、カーネルがスケジューラのカウンタをサンプリングして減衰式で更新します。直近のサンプルほど重みが大きくなります。

**Linuxの特徴：** BSD・Solarisは実行可能スレッドだけをカウントします。Linuxは `D` 状態（割り込み不可待ち——主にI/O待ち、カーネルロック待ち、NFS待ち）のスレッドも含めます。つまりLinuxのロードアベレージが高い場合、CPU飽和ではなくI/O飽和の可能性があります。

```
  負荷 = （実行中スレッド）+ （実行待ちスレッド）+ （D状態スレッド）
                                                    ↑
                                     Linux固有：I/O待ちもカウントされる
```

## What questions does it answer? / 何がわかる？

- システムはベースラインと比べて忙しいか？（CPU数と比較する）
- 圧力は高まっているか（1分 > 5分 > 15分）、回復中か（15分 > 5分 > 1分）？
- 突然のスパイクはCPU起因かI/O起因か？（`/proc/stat` の `iowait` と相関する）
- 現在の実行可能スレッド数は？（`3/412` フィールド）

---

## Key fields to watch / 重点フィールド

| フィールド | 意味 |
|---|---|
| 1分平均 | 直近の圧力。最も変化が速い。バースト系ワークロードでノイジーになりやすい。 |
| 5分平均 | 中期的トレンド。インシデント相関に最も使いやすい。 |
| 15分平均 | バックグラウンドトレンド。安定したベースラインとして比較に使う。 |
| 実行可能/総数 | `3/412` は実行可能・実行中が3スレッド、総数412。実行可能数 > CPU数 ＝ 競合発生中。 |

**経験則：** 負荷 ÷ CPU数。4CPUのシステムで負荷4.0は完全利用。同じシステムで8.0ならスレッドが待っている。1.0は平均1CPUが忙しいことを意味する。

ただしロードアベレージ単独では「なぜ」かはわかりません。8.0はCPU負荷のスレッド8本かもしれないし、低速NFSマウントでブロックしているスレッド8本かもしれない。

## How to read it directly / 直接読む方法

```sh
cat /proc/loadavg

# uptimeコマンドでコンテキストつきで確認
uptime

# 比較用のCPU数
nproc
```

CPU負荷かI/O負荷かを区別するには `/proc/stat` の `iowait` を確認します：

```sh
# iowait%が高い = I/OブロックのスレッドがロードアベレージをInflateしている
grep 'cpu ' /proc/stat
# 列: user nice system idle iowait irq softirq steal guest
```

## A real episode / 実際のエピソード

03:45にアラートが発火：16CPUのホストでロードアベレージが18.2に達した。オンコールエンジニアがCPUを確認したが、全コア30%未満。計算の問題ではない。

1分平均は急上昇しているのに15分平均はまだ2.0前後——突発的なイベントで、じわじわした積み上がりではない。`/proc/loadavg` の実行可能フィールドは `4/890`：890スレッド中、実行可能なのは4スレッドだけ。残り886はスリープしているが、なぜそんなにD状態が多いのか？

`/proc/stat` で `iowait` が68%だった。`dmesg` を見ると1本のディスクにEXT4エラーが発生していた。故障しかけたドライブがカーネルI/Oパスをタイムアウトさせ、割り込み不可待ちでブロックするスレッドが連鎖していた。ロードアベレージはCPUメトリクスが完全に見逃したI/O障害を正直に報告していた。
