# devices

## NAME
`diskstats.devices` - `diskstats` の指標シグナル（devices）

## なぜ今読むか
平均throughputとtail遅延が矛盾するストレージ症状の時に読みます。
queue起因かデバイス遅延か不明なら、filesystemノブ変更前にここで整理します。

## 証拠の順序
1. 先にユーザー症状と時刻窓を固定する。
2. この記事の主シグナルのトレンドを確認する。
3. 隣接シグナル1つと跨層シグナル1つで照合する。
4. 可逆な緩和策を当て、回復トレンドを検証する。

- ID: `diskstats.devices`

## 運用上の意味（ストレージ視点）
この field は、平均値に埋もれる前に、queue膨張とデバイス処理劣化を分離するのに最も有効です。

## フィールドエピソード（ストレージ視点）
単体では静かに見える field でも、時系列文脈で運用判断が変わりました。

`devices` の実務価値は、証拠の時間順を整理することで出ます。何が先に動き、何が後追いし、対策後に何が変わったかを追ってください。

## 読み取りプロトコル（ストレージ視点）
1. 現在の方向（上昇/下降/横ばい）と短期勾配を確認する。
2. `diskstats` の隣接 field と比較して単独判断を避ける。
3. 別 source から queue/stall/pressure 指標を1つ照合する。
4. 指標変化をユーザー影響（遅延・エラー・スループット）に結びつけてから対応する。

## 判断ヒューリスティクス（ストレージ系）
負荷低下後にすぐ正規化するならバースト起因寄り、戻らないなら持続競合を優先調査します。

## 避けるべき失敗パターン（ストレージ系）
- queue/待ち状態の単一スナップショットで根因断定する。
- ストレージ時系列で緩和後回復カーブを追わない。
- ストレージ相関を因果と誤認する。

## アクションループ
1. `devices` に対する反証可能な仮説を置く。
2. 可逆な緩和策を適用する。
3. 2〜3 の相関 field を複数リフレッシュで検証する。
4. ポストモーテム再利用のため証拠メモを残す。

## Unix内部システム視点

この field は **ブロック層キューと完了挙動の発露** です。

- カーネル経路: bio -> request queue -> driver -> device 完了。
- 主な契機: queue depth 増加、R/W競合、firmwareばらつき。
- 併読: iowait、writeback、app timeout。

## 失敗分岐（ストレージ系）
- 分岐1: 症状は改善したがストレージトレンドは不変。 -> ストレージ因果レイヤー仮説を再検証。
- 分岐2: ストレージトレンドは改善したが症状は不変。 -> CPUまたはネットワークの並行連鎖を探索。
- 分岐3: 対策後に両方悪化。 -> 即ロールバックしストレージ証拠スナップショットを保全。
- 分岐4: 一時回復後に再悪化。 -> queueとretryのフィードバックループ確認。

## ソース別ドリルブック（ストレージ系）

### ドリル手順
1. queue depth、待ち分布、service周期を同一タイムラインで追う。
2. バースト生成側の揺れと、デバイス側の恒常遅延を分離する。
3. p99悪化が merge効率か flush周期のどちら由来か検証する。
4. 重い調整の前に、可逆なバースト平滑化を1つ適用する。
5. 調整神話を避けるため、before/afterの痕跡を保全する。

## 失敗類型マトリクス
- 類型A: throughput低下より先に queue depth が膨張する状態。
