# load_1min

[English version](../en/loadavg.load_1min.md)

---

## これは何？

`load_1min` は、カーネルのランキューにいるプロセス数の1分間指数移動平均です。CPUで実行中のプロセスと、CPUを待っているプロセスの両方をカウントします。値は `/proc/loadavg` の先頭フィールドから読み取られます。

今この瞬間にCPUを使おうとしている人数の「頭数」と思ってください。4コアのマシンでロード4.0なら全コアが埋まっています。ロード8.0なら2倍のプロセスがコアを奪い合っている状態です。

```
  ロードアベレージ = 実行中 + CPUを待っている + I/Oを待っている（Linux固有！）
                    ^^^^^^^^  ^^^^^^^^^^^^^^^   ^^^^^^^^^^^^^^^^^^^^^^^^
                    CPU上      ランキュー         Dステート（ディスク/ネット待ち）

  4コアのマシン:
    load 2.0  →  50%の処理能力を使用中      （余裕あり）
    load 4.0  →  100%の処理能力を使用中     （満載）
    load 8.0  →  200%——キューが積み上がっている（過負荷）
```

**Linux固有の重要ポイント:** 伝統的なUNIXと違い、Linuxはディスク・ネットワーク待ちでブロックされたプロセス（Dステート）もロードアベレージに含めます。これが鍵です。「load=40でCPUは暇」という状況はよくあり、その場合の犯人はCPUではなくディスクやNFSです。

---

## なぜ重要？

ロードアベレージはシステム健全性の最も目立つ指標です。`uptime` が最初に表示し、`top` がヘッダーに置き、ほとんどの監視アラートがこれを見ています。

しかし、この値は「嘘をつく」——正確には、話の半分しか語りません。持続的な高負荷はシステムが需要に追いつけていないことを示します。急スパイクの後に素早く回復するなら通常は無害です。1分値は「今」を教えてくれますが、CPUコア数を知らず、CPU律速かI/O律速かも分からなければ対処できません。

**実際の障害シナリオ:** Webサーバーが8コアでload=20を示した。担当者がパニックになりプロセスを次々kill。実際はNFSマウントが遅くなってプロセスが詰まっていたのに、killするたびにサービスが再起動してNFSをさらに叩き、load=60まで上昇。正しい対処は `soft,timeo=` オプションでの再マウントだった。

## 読み方

```sh
uptime
# 10:42:33 up 3 days,  2:17,  2 users,  load average: 3.45, 2.91, 2.58

cat /proc/loadavg
# 3.45 2.91 2.58 4/312 18294
# フィールド: 1分  5分  15分  実行中/合計  最終PID

nproc   # または: grep -c ^processor /proc/cpuinfo
# 8
```

| load ÷ nproc | 意味 |
|---|---|
| < 0.7 | 余裕あり |
| 0.7 – 1.0 | 1コアなら限界、多コアなら問題なし |
| ≈ 1.0 | 満載、余裕なし |
| > 1.5 | 過負荷——リクエストが滞留 |
| > 5.0 | 深刻——まずI/O stallを確認 |

**結論を出す前に CPU iowait を確認する:**
```sh
vmstat 1 5
# wa列（I/O wait%）と b列（ブロック中プロセス数）を見る
# wa高 + load高 = I/Oの問題
# r高  + load高 = CPUの問題
```

## 実際のエピソード

16コアのメディアトランスコードサーバーで、バッチジョブ実行中にload=40を記録。アラートが発火、Slackが騒然とし、オンコールチームはスケールアウトを準備し始めた。誰かが `vmstat 1` を走らせると：

```
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 2 38   ....   ....   ....  .....    0    0  8420   140  ...  ... 3  1 91  5  0
```

`r`（実行待ち）は2。`b`（ブロック中）は38。CPUは91%アイドル。バッチジョブが40本のffmpegプロセスを起動し、全員が遅いHDD RAIDへの読み取りを待っていた。高速なNVMeスクラッチボリュームを追加したところ、2分以内にload=40→3に落ちた。

**教訓:** loadが高くてCPUが暇なら、CPUを見るのをやめてストレージを見る。

## 高い時にやること

**ステップ1: CPUコア数を確認する。**
```sh
nproc
```
全ての判断をこの数値に対してスケールさせること。2コアでload=10は大惨事。32コアでload=10は特筆すべきことではない。

**ステップ2: CPU律速かI/O律速かを判断する。**
```sh
vmstat 1 3
# wa > 20% かつ load 高 → I/Oのボトルネック
# r  > nproc かつ load 高 → CPUのボトルネック
```

**ステップ3: ブロックされているプロセスを探す（I/O経路）。**
```sh
# Dステート（uninterruptible sleep）のプロセスを探す
ps aux | awk '$8=="D"' | head -20
```

**ステップ4: I/Oが原因なら——どのデバイスかを特定する。**
```sh
iostat -x 1 5
# %util が100%に近く、await が高いデバイスを探す
```

**ステップ5: CPUが原因なら——何が消費しているかを探す。**
```sh
top -H    # スレッドレベルの表示
perf top  # 利用可能な場合
```

## よくある間違い

**nproc を確認せずに数値だけを見てパニックになる。** ロードアベレージはコア数を知らなければ意味がない。常に `nproc` で割ってから判断する。

**loadが高い＝CPUがボトルネックと思い込む。** LinuxではI/O待ちプロセスもloadにカウントされる。必ず `vmstat` の `wa` 列と `b` 列を先に確認する。

**load_1min を安定した指標として扱う。** 1分値は変動が大きい。単一の読み取り値8.0は10秒のバーストの末尾かもしれない。トレンドを見るには load_5min と load_15min を使う。

**loadを下げようとプロセスをkillする。** I/Oでブロックされているプロセスをkillすると、サービスが再起動してloadがさらに上がることが多い。先にI/Oの原因を直す。

**絶対値でアラートを設定する。** `load > 10` というアラートはコア数の違うマシンにまたがると無意味。代わりに `load / nproc > 1.5` でアラートを設定する。

## 関連項目

- `loadavg.load_5min` — トレンド方向を見るための5分平均
- `loadavg.load_15min` — 持続的な負荷を確認する15分平均
- `loadavg.running_threads` — 現在の実行可能プロセス数（瞬間値）
- `stat.cpu_iowait` — loadがI/O律速かを確認する
- `pressure.cpu_some_avg10` — より精密なCPU競合シグナル（PSI）
- `pressure.io_some_avg10` — loadへのI/O stall寄与を確認する
