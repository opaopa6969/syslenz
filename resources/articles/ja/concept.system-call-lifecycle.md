## コア概念
アプリの処理は最終的にシステムコールとしてカーネルと対話します。入口、カーネル処理、必要なら sleep/wakeup、そしてユーザー空間への復帰です。

## なぜ観測で重要か
遅延悪化は純粋なユーザー空間 CPU ではなく「遷移コスト」に潜みます。
- user->kernel 境界コスト
- sleep 中のスケジューラ待ち
- wakeup/割り込み到達タイミング

## エピソード: 「コードは速いのに現実は遅い」
ハンドラ最適化後も tail latency が改善しないケース。
- user-space profiler はきれい。
- `read`/`write`/`epoll_wait` など syscall 主体の壁時間が長い。
- 割り込みと runqueue 証拠から wakeup 遅延が判明。

不足していたのはコード品質ではなく syscall ライフサイクル視点でした。

## /proc をこの視点で読む
1. 症状を syscall 系列（I/O, network, memory, process）に対応づける。
2. 同時刻の scheduler/interrupt シグナルを確認する。
3. CPU使用と「実行待ち」「イベント待ち」を分離する。
4. 緩和策で時間消費箇所がどう移動したかを検証する。

## 失敗パターン
- 待ち状態主因なのにアプリコードだけを責める。
- context switch / wakeup コストを無視する。
- ワークロード文脈なしに syscall 回数だけで善悪判断する。

## 実務プレイブック
1. 支配的な block/wakeup 点を特定する。
2. queue depth / pressure / runqueue と相関確認する。
3. 不要遷移を減らす（batching、接続再利用、async設計）。
4. マイクロベンチでなく E2E 体感で再計測する。

### Unix内部との接続（システム）
- process model（システム視点）: runnable が増えたのか、blocked が滞留したのか。
- syscall lifecycle（システム視点）: request時間は entry/sleep/wakeup/return のどこへ移ったか。
- interrupt path（システム視点）: wakeup配送や softirq backlog が tail を押し上げたか。
- scheduler（システム視点）: fairness は throughput を守りつつ tail を悪化させていないか。
