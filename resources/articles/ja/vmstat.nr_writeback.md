# nr_writeback

[English version](../en/vmstat.nr_writeback.md)

---

## これは何？

`nr_writeback` は現在**ディスクへの書き込みが進行中の**メモリページ数を計上します。フライト中の書き込みです。これらはすでにdirtyとしてマークされ、カーネルがフラッシュを開始したものの、まだ書き込みが完了していないページです。

`nr_dirty` が処理待ちの仕事のキューだとすれば、`nr_writeback` は現在進行中の仕事です。

```
  書き込みパイプライン：

  アプリがデータを書き込む
       │
       v
  ページキャッシュ（RAM）
  [dirty] [dirty] [dirty]   <- nr_dirty: フラッシュ待ち
       │
       │ カーネルがフラッシュを開始（pdflush / kworker）
       v
  [writeback] [writeback]   <- nr_writeback: 今書き込み中
       │
       v
  ディスク（永続ストレージ）  <- 書き込み完了、ページはcleanになる
```

荷さばき場の荷物に例えると：`nr_dirty` は積み上がったトラック待ちの箱、`nr_writeback` は今まさにトラックに積まれている箱です。

---

## なぜ重要？

`nr_writeback` 単体は警戒信号ではありません。書き込みワークロード中にフライト中のページが多少あるのは完全に正常です。シグナルは `nr_dirty` と**合わせて**読み、時間的な関係を見ることで生まれます。

**パターン1：両方が高くて動いている。** フラッシュがアクティブで概ねキープアップしている。重い書き込み負荷では正常。`nr_dirty` が `nr_writeback` で排出できる速さより速く増えていないか見ること。

**パターン2：`nr_dirty` が高く、`nr_writeback` がゼロ近傍。** これが危険サインです。dirtyページが積み上がっているのに、ディスクには何も書かれていない。起こりうる原因：ストレージデバイスが飽和、I/Oエラー、NFSマウントが応答なし、またはファイルシステムがエラー状態。カーネルがアプリケーションをスロットル（書き込みストール）している可能性があります。

**パターン3：`nr_writeback` が持続的に高い。** フラッシュパイプラインが常に満杯 — ストレージが書き込みを十分速く受け取れない。時間とともに `nr_dirty` にバックアップし、最終的に `write()` でアプリケーションがブロックする書き込みスロットルが発生します。

```
  nr_writeback が継続的に高い → ストレージボトルネック：

  ▲ ページ数
  │         nr_dirty  ___________
  │                  /           \
  │  nr_writeback ~~~~~~~~~~~~~~~~~~~  <- 常に上限付近
  │
  └────────────────────────────────▶ 時間
    （「トラックは常に満杯、箱は増え続ける」）
```

## 読み方

```sh
# 両フィールドをリアルタイムで見る
watch -n 1 'grep -E "nr_dirty|nr_writeback" /proc/vmstat'

# または vmstat で
vmstat -m 1   # writebackを含むメモリ統計を表示

# 書き込みスループットを確認（フラッシュは進んでいるか？）
iostat -x 1 | grep -v '^$'
```

| `nr_writeback` | `nr_dirty` | 解釈 |
|----------------|------------|------|
| 低い | 低い | 有意な書き込み活動なし |
| 低〜中 | 中〜高 | 書き込みバックログ蓄積中。トレンドを監視 |
| 高い（動いている） | 低下中 | フラッシュが走っている。健全な排出 |
| 高い（安定） | 上昇中 | ストレージが追いつかない。ストール注意 |
| ゼロ近傍 | 高い | フラッシュが停止 — ディスク/エラーを確認 |

**単位：** ほとんどのシステムで1ページ = 4KB。10,000ページ = フライト中40MB。

```sh
# ページ数をMBに変換
echo $(( $(grep nr_writeback /proc/vmstat | awk '{print $2}') * 4 / 1024 )) MB
```

## 実際のエピソード

あるロギングインフラチームが、Elasticsearchノードの書き込みパフォーマンスが低下していることに気づいた。インデックス登録のレイテンシが48時間で2倍になっていた。CPUは正常。メモリも正常。ネットワークも正常。

誰かが `nr_writeback` を確認した：
```
nr_dirty      12450
nr_writeback    0
```

dirtyページが12,000以上積み上がっているのに、ディスクには何も書かれていない（`nr_writeback` がゼロ）。`iostat` はデータディスクの使用率を0%と表示していた。ディスクはアイドルに見えた。

`dmesg` が答えを示した：
```
EXT4-fs error (device sdb1): ext4_find_entry:1455: inode #2: comm kworker: reading directory lblock 0
```

ファイルシステムがエラー状態になり、すべての書き込みを静かに停止していた。カーネルはデータをページキャッシュに受け入れていた（アプリケーションはまだ失敗していない）が、ディスクには何も届いていなかった。`fsck` とリマウントで解決した。

**教訓：** `nr_writeback = 0` で `nr_dirty` が上昇しているのは、書き込み活動が少ないサインではない。書き込みが完全に停止しているサインかもしれない。このパターンを見たら必ず `dmesg` とクロスチェックすること。

## 異常な時にやること

**ケースA：`nr_writeback` が高く `nr_dirty` も上昇中（ストレージ飽和）**
```sh
# 飽和しているデバイスを特定
iostat -x 1 5
# %utilが100%近い、awaitが高い、を探す

# どのプロセスが書き込んでいるか
iotop -aoP

# 一時的に書き込み圧力を下げる
ionice -c 3 -p <PID>   # 重い書き込みプロセスの優先度を下げる
```

**ケースB：`nr_writeback` がゼロ近傍で `nr_dirty` が上昇中（フラッシュ停止）**
```sh
# ファイルシステムエラーを確認
dmesg | tail -30 | grep -iE "error|EIO|timeout|reset|abort"

# デバイスは健全か？
smartctl -a /dev/sda

# スタックしたマウントを確認（NFSか？）
df -h   # NFSが応答しないならハングする
mount | grep nfs
```

**ケースC：定期的にスパイクして低下する（フラッシュストーム）**
```sh
# dirty_ratioの閾値によってトリガーされる
sysctl vm.dirty_background_ratio vm.dirty_ratio

# バックグラウンドフラッシュをより積極的にしてバースト量を削減
sysctl vm.dirty_background_ratio=5   # デフォルトは10
```

## よくある間違い

**「低く見える」から無視する。** 書き込みワークロード中の `nr_writeback = 0` は安心サインではなく異常だ。フラッシュが停止している可能性がある。

**`nr_dirty` なしに `nr_writeback` だけ見る。** 2つは合わせて読まなければならない。`nr_dirty` が1,000で `nr_writeback` が5,000ならフラッシュが勝っている。`nr_dirty` が50,000で上昇中の状態で同じ `nr_writeback` なら負けている。

**高いwriteback = 悪いと決めつける。** `sync` やfsync重視のワークロード中は `nr_writeback` が高くなり、それは予期された状態だ。問題かどうかはアプリケーションレベルの症状（書き込みレイテンシ、ブロッキングコール）で判断すること。

## 関連項目

- `vmstat.nr_dirty` — フラッシュ待ちのdirtyページ。常にnr_writebackと合わせて読む
- `vmstat.nr_dirty_threshold` — アプリケーションの書き込みがストールする前の計算された上限
- `pressure/io_some_avg10` — I/O圧力が実際にタスクをストールさせているか確認
- `diskstats` — デバイスごとの書き込みスループット、使用率、キュー深度
