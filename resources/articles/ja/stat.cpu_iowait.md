# cpu_iowait

[English version](../en/stat.cpu_iowait.md)

---

## これは何？

`cpu_iowait` は、CPUが**アイドル状態でI/Oの完了を待っていた**時間の割合です。Linuxのパフォーマンス監視において最も誤読されやすい指標の一つです。

核心的な区別：iowaitはCPU実行時間ではありません。*アイドル*時間です — 実行可能なタスクがすべてディスクやネットワークのI/O待ちでブロックされているため、CPUが何も実行できなかった時間です。CPUは生産的なことを何もしていませんが、待っている仕事があるため他のことも実行できません。

```
  iowaitが実際に何を指すか：

  プロセスA: [実行][実行][ ディスク読み込み待ち ][実行]
  プロセスB: [実行][  ディスク読み込み待ち       ][実]
  CPU:       [忙  ][忙  ][ アイドル — iowait    ][忙]

  CPUは空いているが、実行可能なものがない。
  このアイドル時間がiowaitとして計上される。
```

部品の到着を待つ組み立てラインの作業者のようなものです。作業者（CPU）は何もしていません。でも怠けているわけではない。ボトルネックは部品の供給業者（ストレージ）にあります。

---

## なぜ重要？

**iowait高い = ストレージが遅い、CPUではない。** これが核心です。iowaitが高い時、より速いCPUやコアを追加しても何の効果もありません。システムはデータがストレージとRAMの間を移動する速さによって制限されています。

iowaitが急増する典型的なシナリオ：
- データベースクエリがキャッシュにないテーブルにヒット — コールドデータをディスクから読む
- ログローテーションやバックアップジョブが大きなファイルを書き込む
- アプリケーションがリクエストごとに設定ファイルを読む（キャッシュすべき）
- バックグラウンドでRAIDリビルドやファイルシステムチェックが動いている
- スワップがアクティブでページがスワップ領域から読み戻されている

**なぜiowaitが「CPUが忙しい」ように見えることがあるのか？** `top` などのツールはサマリーにiowaitを「CPU時間」として含めるからです。`top` が90%のCPUを表示している場合、それは10%のuser + 80%のiowaitかもしれません。CPUはほとんどディスク待ちで座っているだけです。これは80%のuser + 10%のiowaitとは全く異なります。

## 読み方

```sh
# iowaitをコンテキストと合わせて確認
mpstat -P ALL 1 5

# どのディスクが忙しいか
iostat -x 1

# どのプロセスがI/Oをしているか
iotop -a
```

| `cpu_iowait` の値 | 解釈 |
|------------------|------|
| 0〜5% | 無視できる。I/Oは速いか軽い |
| 5〜20% | 中程度。iostatと合わせて監視する価値あり |
| 20〜40% | 高い。ストレージがボトルネックかもしれない |
| 40%超 | 深刻。システムはI/Oバウンドの可能性が高い |

**iowait + iostatのクロスチェック：**

```sh
# 合わせて実行してI/Oが原因かを確認
iostat -x 1 | grep -v '^$'
# 見るべきポイント：%utilが100%に近い、HDD でawait > 10ms、SSD で > 1ms
```

| 状況 | iowait | iostat %util | 意味 |
|------|--------|--------------|------|
| 正常 | 低い | 低い | 健全 |
| ストレージボトルネック | 高い | ~100% | ディスク飽和 |
| I/Oバースト（SSD） | スパイク後低下 | スパイク後低下 | 一時的。監視継続 |
| 原因不明のhigh iowait | 高い | 低い | NFS、ネットワークストレージを確認 |

## 実際のエピソード

あるECプラットフォームが6ヶ月間快適に動いていた。ある日チームにアラートが届いた：「CPU使用率92%」。エンジニアたちはアプリケーションコードのプロファイリングを始め、JVM設定を調整し、インスタンスタイプのアップグレードを議論し始めた。

調査開始から3時間後、誰かが `mpstat -P ALL 1` を実行してこんな数字に気づいた：`%usr` は11%、`%sys` は1%、しかし `%iowait` は80%。合計が92%になっていたので、監視が「CPU」アラートを発火していたのだ。

素早く `iostat -x 1` を実行すると、1つのディスクが使用率100%になっていた。原因は02:00に開始したスケジュール済みのウイルス対策スキャンが、アプリケーションのセッションファイルを格納している `/var` ディレクトリ全体をスキャンし続けていたことだった。

修正：スキャンを05:00（トラフィックが下がった後）に再スケジュールし、セッションファイルのディレクトリを除外。`cpu_iowait` は2%に下落。コード変更もハードウェアアップグレードも不要だった。

**教訓：** 誰かが「CPUが90%」と言ったら、必ず聞くこと：「そのうちどれがiowaitですか？」 答えがすべてを変える。

## 高い時にやること

**ステップ1：I/Oが本当の原因か確認する。**
```sh
iostat -x 1 5
# 見るべきポイント：%util（飽和度）、await（遅延ms）、r/s と w/s（スループット）
```

**ステップ2：どのデバイスとプロセスかを特定する。**
```sh
# どのデバイスが飽和しているか
iostat -x 1 | sort -k 14 -rn | head -5

# どのプロセスがI/Oしているか
iotop -aoP
```

**ステップ3：I/Oを分類する。**
- 読み込みか書き込みか？（iostatの `r/s` vs `w/s`）
- シーケンシャルかランダムか？（`rrqm/s` と `wrqm/s` のマージ率を確認）
- アプリコードから？バックグラウンドジョブ？それともOSそのもの？

**ステップ4：原因に基づいて対処する。**

```sh
# 特定プロセスが犯人なら、I/O優先度を制限する
ionice -c 3 -p <PID>   # アイドル優先度：他に譲る

# スワップが寄与していないか確認（vmstatのpswpin/pswpout）
vmstat 1 5

# カーネルレベルでスタックしたI/Oを確認
cat /proc/diskstats
dmesg | grep -i "error\|timeout\|reset" | tail -20
```

**ステップ5：ハードウェアの検討。**
- HDD：awaitが20msを超えたら問題。SSD移行を検討
- SSD：%utilが継続的に80%超なら、IOPSが不足（ドライブ追加、NVMe使用）
- ネットワークストレージ（NFS、iSCSI）：ディスクではなくネットワーク遅延を確認

## よくある間違い

**「CPUの問題」と呼ぶ。** iowaitはCPUのアイドル時間だ。CPUは正常。ストレージが正常でない。iowaitが問題の時にCPU設定を調整しても意味がない。

**「CPUは実際にアイドルだから問題ない」と無視する。** 確かにCPUは空いているが、アプリケーションはI/O待ちでストールしている。CPUが空いていても、ユーザーは遅さを感じている。

**ネットワークストレージを確認しない。** ローカルディスクの使用率が低いのにiowaitが高い場合、NFSやiSCSIが遅い可能性が高い。`iostat` はNFSを表示しない。`nfsstat` や `mountstats` が必要。

**I/O負荷の高いプロセスをパニックで強制終了する。** バックアップジョブがiowaitを引き起こしている場合、途中で強制終了するとデータが不整合状態になる可能性がある。代わりに `ionice` でスロットルすること。

## 関連項目

- `stat.cpu_user` — ユーザー空間CPU時間。high user + high iowaitは典型的な誤報パターン
- `vmstat.pgpgin` / `vmstat.pgpgout` — ページレベルI/Oカウンター。上昇はスワップやファイルI/Oを意味する
- `vmstat.pswpin` / `vmstat.pswpout` — スワップI/O。上昇するとiowaitはスワップ起因かもしれない
- `diskstats` — 飽和しているデバイスを特定するためのデバイスごとのI/O統計
- `pressure/io_some_avg10` — カーネルPSI。I/O圧力が実際にタスクをストールさせているか確認
