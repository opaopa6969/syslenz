# cpu_some_avg10

[English version](../en/pressure.cpu_some_avg10.md)

---

## これは何？

`cpu_some_avg10` は、カーネル4.20で導入されたLinuxの **PSI (Pressure Stall Information)** の一部です。直近10秒間のうち、少なくとも1つのタスクがCPUを待っていた時間の割合を計測します——すべてのコアが埋まっていて実行できなかった時間です。

スケールは0〜100%。値が5.0なら、直近10秒の5%の時間、少なくとも1つのプロセスが実行可能な状態でCPUを取得できなかったことを意味します。

```
  PSIは利用率ではなく実際の「待ち時間」を計測する:

  CPU利用率:       ████████████████████░░░░  80%が使用中
                   ↑ 従来の指標——プロセスが待っているかどうかは分からない

  cpu_some_avg10:  ████░░░░░░░░░░░░░░░░░░░░  15%の時間、誰かが待っていた
                   ↑ PSI——「プロセスが遅延したか？」を直接計測する
```

**PSIがロードアベレージよりCPU圧力の計測に優れている理由:** ロードアベレージはランキューのプロセス数をカウントしますが、実際の遅延量は分かりません。PSIはプロセスがstallした時間を計測します。load=2.0でcpu_some_avg10=40%のシステムはプロセスを飢餓状態にしています。load=6.0でcpu_some_avg10=2%のシステムは忙しいが誰も傷つけていません。

`avg10` サフィックスは10秒の指数移動平均を意味します。`avg60`（1分）と `avg300`（5分）のバリアントもあります。

---

## なぜ重要？

ロードアベレージはCPU圧力について嘘をつきます——特にI/O待ちプロセスが値を膨らませるとき。PSIは嘘をつきません: スケジューラ遅延の直接計測です。

**PSIが輝く場面:**
- CPU利用率70%、cpu_some_avg10=0.5%のシステム: プロセスはうまくスケジュールされており、飢餓なし。
- CPU利用率50%、cpu_some_avg10=30%のシステム: 何かが直列化されている——ロック競合、特定CPUへのピニング、cgroupのノイジーネイバー干渉。

**SLO予算として:** PSIはLinuxのcgroup CPUスロットリングとFacebookの `oomd` の判断根拠になる指標です。レイテンシSLOを構築するなら、`cpu_some_avg10` はプロセスが遅延した時間の割合を直接教えてくれ、p99レイテンシに直接マッピングできます。

**ノイジーネイバー検出:** コンテナ環境では、cgroupレベルの `cpu_some_avg10` がどのコンテナがCPU飢餓を経験しているかを、システム全体のCPU%が正常でも明らかにします。

## 読み方

```sh
cat /proc/pressure/cpu
# some avg10=2.45 avg60=1.83 avg300=1.20 total=12345678
# full avg10=0.00 avg60=0.00 avg300=0.00 total=0
```

**`some` vs `full`:**
- `some`: 少なくとも1つのタスクがCPUを待っていた（1つ以上のプロセスが遅延）
- `full`: すべての非アイドルタスクが同時にCPUを待っていた（システム全体のstall——非常に深刻）

CPUでは `full` はほぼ常に0です（I/Oでは一般的、CPUでは珍しい）。CPU圧力には `some` に集中します。

**実用的な閾値:**

| cpu_some_avg10 | 解釈 |
|---|---|
| 0 – 5% | 健全——CPU競合は最小限 |
| 5 – 20% | 中程度の圧力——持続した場合は監視 |
| 20 – 40% | 高い——レイテンシへの影響が出やすい、ランキューを調査 |
| > 40% | 深刻——プロセスが飢餓状態、即対応が必要 |

これはガイドラインです。レイテンシ敏感なリアルタイムサービスは5%超を気にするかもしれません。バッチジョブは40%超を許容するかもしれません。

## 実際のエピソード

GoのマイクロサービスがSLO 50msに対してp99レイテンシ180msを記録していた。CPU利用率は45%——従来の常識では余裕十分。8コアマシンでロードアベレージは3.2。ダッシュボードは黄色で赤ではなかった。

エンジニアが実行：
```sh
cat /proc/pressure/cpu
# some avg10=38.2 avg60=35.1 avg300=29.8 total=...
```

CPU `some` 圧力が38%。時間の38%以上、プロセスがCPUスロットを待っていた。原因: サービスがCPU limit 2000m（2コア）のKubernetesポッドで動いていた。アプリケーションはgoroutineを大量に生成していたが、ノードが8物理コアを持っているにもかかわらず2つの仮想CPUを奪い合っていた。

CPU limitを4000mに上げると `cpu_some_avg10` が4.1%に落ち、p99レイテンシが48ms——SLO以下——になった。

**教訓:** CPU圧力（`cpu_some_avg10`）は利用率が安全に見えても競合を明らかにする。CPUが十分あると思う前にcgroupのCPU limitを確認する。

## 高い時にやること

**ステップ1: スパイクではなく持続していることを確認する。**
```sh
# 3つの平均を全部監視する
watch -n 5 'cat /proc/pressure/cpu'
# avg10が高くてもavg300が低ければ直近のバースト
```

**ステップ2: CPU limitが制約になっていないか確認する。**
```sh
# コンテナ/cgroup環境で
cat /sys/fs/cgroup/cpu/cpu.cfs_quota_us
cat /sys/fs/cgroup/cpu/cpu.cfs_period_us
# quota/period < コア数 = スロットリングの可能性
```

**ステップ3: どのプロセスがCPUを消費しているかを探す。**
```sh
top -H        # スレッドレベル、CPU使用率でソート
pidstat 1 5   # 時系列でのプロセスごとのCPU使用
```

**ステップ4: CPUピニングやNUMAの問題を確認する。**
```sh
taskset -p <pid>   # このプロセスが使えるCPUはどれ？
numastat           # NUMAメモリアクセスパターン
```

**ステップ5: スケジューラ統計を確認する。**
```sh
# CPU別のランキュー長を確認
cat /proc/schedstat
sar -q 1 5   # sysstatsがインストールされていれば
```

## よくある間違い

**ロードアベレージが大丈夫なのでPSIを無視する。** ロードアベレージはcgroupのCPU limitやCPUピニングを見えません。PSIは見えます。コンテナを動かしているなら、個々のポッドが飢餓状態でもロードアベレージは正常に見えます。

**`cpu_some_avg10` をCPU利用率と混同する。** PSI 38%はCPU利用率38%ではありません。時間の38%に少なくとも1つのプロセスが遅延した——全体のCPU利用率が低くても——という意味です。

**ゼロでない値すべてを問題と扱う。** 多テナントの忙しいシステムでは、`cpu_some_avg10` が2〜5%は正常で無害です。20%を超えてユーザー可視のレイテンシと相関するときに心配する。

**`avg60` と `avg300` を無視する。** `avg10` が高くて `avg300` が低いなら直近のバーストです。`avg300` が高いなら慢性的な問題です。どちらも重要ですが、意味が異なります。

## 関連項目

- `pressure.cpu_full_avg10` — すべてのタスクが同時にstall（極端なケース）
- `pressure.cpu_some_avg60` — 1分間平滑化したCPU圧力の表示
- `loadavg.load_1min` — 従来の代替手段（cgroupコンテキストでは精度が低い）
- `stat.cpu_iowait` — I/O waitと実際のCPU圧力を分離する
- `schedstat.runqueue_distribution` — CPU別のキュー深さの時系列
