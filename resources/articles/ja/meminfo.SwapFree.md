# SwapFree

[English version](../en/meminfo.SwapFree.md)

---

## これは何？

`SwapFree` は、スワップパーティションまたはスワップファイルに残っている未使用スペースです。スワップとは、カーネルがRAMから追い出した匿名メモリページを保持するために確保されたディスクスペースです。

スワップは綱渡りの下のセーフティネットと考えてください——完全な墜落を防ぎますが、決してそこに落ちたくはありません。スワップは追加RAMではありません。NVMe SSDでも、スワップはRAMより**10〜100倍遅い**です。

```
  RAM：ナノ秒単位のアクセス
  ┌──────────────────────────────────────┐
  │ アプリA │ アプリB │ キャッシュ │ 空き │
  └──────────────────────────────────────┘
                ↓ カーネルがアプリBをスワップへ追い出す
  スワップ（ディスク）：マイクロ秒〜ミリ秒のアクセス
  ┌────────────────────┐
  │ アプリB（ページング済）│ SwapTotal - SwapFree
  └────────────────────┘
```

`SwapFree = SwapTotal - （現在使用中のスワップ）`

---

## なぜ重要？

**SwapFree が時間とともに減り続けているなら、システムはスワップ使用量を積み重ねています。** 戻らなければ何かがメモリをリークしています。増えたり減ったりするなら（スワップが満杯になって回復を繰り返す）、システムは圧力を受けているものの回復しています。

**本当の危険は SwapFree = 0 ではなく、活発なスワップI/Oです。** スワップに2 GBあるが活発なスワッピングがないシステムは安定しています。500 MBがスワップにあり `vmstat` が `so=50`（毎秒50ページスワップアウト）を示すシステムは活発なストレス下にあります——アプリケーションがスローモーションで動いています。

**SwapFree = SwapTotal（スワップ未使用）が理想的ですが**、それが安全を意味するわけではありません——まだスワップが必要になっていないだけかもしれません。先行指標として `MemAvailable` を監視してください。

## 読み方

```sh
# スワップ状況
grep -E "SwapTotal|SwapFree|SwapCached" /proc/meminfo

# 使用中スワップのパーセンテージ
awk '/SwapTotal/{t=$2} /SwapFree/{f=$2} END{
  if(t>0) printf "スワップ使用: %.1f%%\n", (t-f)/t*100
  else print "スワップ未設定"
}' /proc/meminfo

# 最重要：使用量だけでなく実際のスワップI/Oを確認
vmstat 1 10
# si = 毎秒ディスクからスワップインされたページ数
# so = 毎秒ディスクにスワップアウトされたページ数
# so がゼロ以外 = 今まさにページングが起きている
```

| 状況 | 対応 |
|------|------|
| SwapFree = SwapTotal, so=0 | 健全——スワップ未使用 |
| SwapFree < SwapTotal, so=0 | スワップ使用中だが非活発——トレンドを監視 |
| SwapFree が着実に低下 | メモリリーク——AnonPages で確認 |
| so > 0 が続く | 活発な圧力——今すぐ調査 |
| SwapFree = 0, so > 0 | 危機的——OOM間近 |

## 実際のエピソード

16 GBサーバーで動くRedisインスタンスが6ヶ月間問題なく動いていました。運用チームはクエリレイテンシが2週間かけて0.5msから3msへじわじわ上昇しているのに気づきました。CPUやネットワークのグラフには何も出ていませんでした。

誰かが `vmstat 1` を実行すると `si=12` が見えました——毎秒12ページが着実にスワップから読み戻されていました。`SwapFree` は4 GB中1.4 GBが使用中と表示。それ自体は警戒するほどではありません。しかし `so` と `si` が24時間ゼロ以外でした。

原因：Redisは `maxmemory` を12 GBに設定されていましたが、OSも複数のバックグラウンドジョブを動かしており、数週間かけて4 GBの匿名ページが積み重なっていました。カーネルは古いRedisページをじわじわスワップに追い出していました。それらのページがアクセスされるとスワップから読み戻す必要があり——レイテンシスパイクを引き起こしていました。

修正：バックグラウンドジョブのメモリフットプリントを削減し、カーネルに任せるのではなくRedis内でより積極的に追い出す `maxmemory-policy` を設定。

教訓：スワップ使用は長い間サイレントでいられます。本当のシグナルは `SwapFree` ではなく `vmstat` の `si`/`so` です。

## SwapFree が低下している時にやること

**ステップ1：スワップが実際に活発に使われているか確認する（割り当てられているだけでなく）。**
```sh
vmstat 1 10
# si と so 列を見る
```

**ステップ2：メモリを大量消費しているものを見つける。**
```sh
# AnonPages のトレンドを確認——増加しているか？
grep AnonPages /proc/meminfo

# RSSが最も多いプロセスは？
ps aux --sort=-%mem | head -15
```

**ステップ3：どれくらいの期間スワップが増えているか確認する。**
過去の監視データがあれば傾きを確認。着実な緩やかな低下 = リークの可能性。最近の急激な変化 = 負荷スパイク。

**ステップ4：活発なスワッピング（so > 0）がある場合：**
- 短期：リークしているプロセスを特定して再起動するか、他のメモリを解放する
- 中期：RAMを追加するかプロセスごとのメモリ制限を下げる
- スワップを永続的な解決策として頼ってはいけない

**ステップ5：swappiness のチューニングを検討する**（トレードオフを理解した上で）：
```sh
# 現在の設定を確認（デフォルト: 60）
cat /proc/sys/vm/swappiness

# 小さい値 = カーネルがスワップよりもRAMに匿名ページを保持しようとする
# レイテンシ重視ワークロードには 10 が一般的
sysctl vm.swappiness=10
```

## よくある間違い

**スワップを「追加RAM」として扱う。** スワップは緊急時の退避先です。スワップを大きく確保しても、より多くのアプリが動かせるわけではありません——OOMキラーが来るのが、パフォーマンスがすでに大幅に劣化した後に遅れるだけです。

**SwapFree が多く見えるからと活発なスワップI/Oを無視する。** `so=100` で1 GBのスワップ使用は、`so=0` で3 GBの使用より遥かに深刻です。

**swappiness=0 に設定する。** これはカーネルにスワップを完全に避けるよう指示し、必要以上に早くOOMキラーが発動することがあります。`swappiness=10` がより良いトレードオフです。

**本番システムにスワップを設定しない。** スワップなしでは、メモリが尽きた瞬間にOOMキラーが発動します。スワップがあれば、気づいて対応するための劣化はしているが機能している猶予期間があります。

## 関連項目

- `meminfo.SwapTotal` — 設定された総スワップスペース
- `meminfo.MemAvailable` — スワップが増え始める前の先行指標
- `meminfo.AnonPages` — スワップを埋めるもの（匿名ページ）
- `vmstat.si` / `vmstat.so` — 実際のスワップI/Oレート（本物のレイテンシシグナル）
- `pressure/memory_some_avg10` — OOMに先行するカーネルストールシグナル
