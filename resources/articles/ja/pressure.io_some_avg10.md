# io_some_avg10

[English version](../en/pressure.io_some_avg10.md)

---

## これは何？

`io_some_avg10` は、直近10秒間のうち、少なくとも1つのタスクがI/Oを待ってstallしていた時間の割合を計測します——まだ完了していない読み書きでブロックされた時間です。カーネル4.20から利用可能なLinux PSIの一部で、`/proc/pressure/io` から読み取られます。

CPU圧力と違い、I/O圧力には意味のある `full` 指標があります: `io_full_avg10` がゼロでない場合、システム上のすべてのタスクが同時にI/Oを待っていた——CPUが完全にアイドルで、ストレージデバイスだけが動いていた状態を意味します。

```
  io_some vs io_full:

  タスクA: ████░░░░████████░░░░████  （ディスクから読み取り中）
  タスクB: ████████░░░░░░░░████████  （これもディスクから読み取り中）
  タスクC: ██████████████████░░░░░░  （CPUで実行中）

  some: AまたはBがブロックされている窓  → ほとんどの時間
  full: A、B、Cが全員同時にブロックされている窓 → io_full

  io_some_avg10 が捉えるもの: 「誰かがI/Oを待っている」
  io_full_avg10 が捉えるもの: 「全員が待っていて、何も進んでいない」
```

---

## なぜ重要？

I/O圧力は現代のほぼすべてのシステムに隠れた税として存在します。ストレージはRAMの数百〜数千倍遅い。プロセスがディスクI/Oで直列化し始めると、レイテンシは急速に積み上がります——特に書き込みが同期的だったり、複数のプロセスが同じI/Oキューを共有する場合は特に。

**`io_some_avg10` が他の指標では検出できないものを捉える:**

- `iostat %util`: デバイスがどれだけ忙しいかを示すが、NVMeの100%利用率はプロセスがstallしていることを意味しない——キュー深さがリクエストを高速にさばいていることがある。
- `vmstat` の `iowait`: I/O中のCPUアイドル時間を示すが、CPUごとの値でマルチコアシステムでは誤解を招く。
- `io_some_avg10`: 「プロセスが実際に待ったか？」を直接計測する。代理指標ではない。答えはイエスかノーで、時間で計測される。

**full/someの分離が深刻度を示す:** `io_some_avg10 = 20%` で `io_full_avg10 = 0%` は、I/O圧力はあるがシステムは部分的に前進できている。`io_some_avg10 = 20%` で `io_full_avg10 = 15%` は、システムが頻繁に「何も進まない」状態にある——即座に対応すべきストレージのボトルネックです。

## 読み方

```sh
cat /proc/pressure/io
# some avg10=8.42 avg60=6.71 avg300=3.14 total=123456789
# full avg10=1.23 avg60=0.98 avg300=0.41 total=23456789
```

**実用的な閾値:**

| io_some_avg10 | io_full_avg10 | 解釈 |
|---|---|---|
| 0 – 5% | 0% | 通常のI/O活動 |
| 5 – 20% | 0% | 中程度のI/O圧力——監視する |
| 20 – 50% | 0 – 2% | 高い圧力——デバイスとワークロードを調査 |
| > 50% | 0 – 5% | 深刻——I/Oがボトルネック |
| どの値でも | > 5% | 危機的——ストレージがシステム全体の進行をブロック |

## 実際のエピソード

PostgreSQLサーバーが断続的なクエリタイムアウトに悩まされていた——一貫性がなく、クエリの複雑さとも相関がなく、ただ1時間に数回の10〜30秒のタイムアウトが起きていた。データベースチームは接続プールの枯渇、ロック待ち、クエリプランを確認した。明らかな問題はなかった。

opsエンジニアがPSIを確認：
```sh
watch -n 2 'cat /proc/pressure/io'
```

```
some avg10=52.3 avg60=41.8 avg300=22.6 total=...
full avg10=18.7 avg60=14.2 avg300=7.1  total=...
```

`io_full_avg10` が18.7%——5秒に1秒近く、システム全体がI/Oを待ってアイドルになっていた。だからクエリがタイムアウトした: ストレージキューが飽和していると、単純なルックアップでさえstallする。

```sh
iostat -x 1 5
```

ディスクは `%util=99%`、`await=280ms`（I/O操作あたりの平均待ち時間）。PostgreSQLのデータディレクトリがシステムログと同じディスクにあった。ログを大量に書くアプリケーションが毎時ギガバイト単位のログを書き、HDDを飽和させていた。

修正: ログを別のディスクに移動。`io_full_avg10` が0.2%まで落ち、クエリタイムアウトが消えた。

**教訓:** `io_full_avg10` が高いのは、ストレージがボトルネックであるという最も明確なシグナルの一つ。アプリケーションレベルのタイムアウトがPSIが既に知っていることを教えるのを待つ必要はない。

## 高い時にやること

**ステップ1: `some` と合わせて `full` を確認する。**
```sh
cat /proc/pressure/io
```
`full_avg10` > 5%なら即座に優先——ストレージデバイスが飽和している可能性が高い。

**ステップ2: 飽和しているデバイスを特定する。**
```sh
iostat -x 1 5
# %utilが100%近く、awaitが20ms超（HDD）または1ms超（NVMe）のデバイスを探す
# awaitとutilが最も高いデバイスがボトルネック
```

**ステップ3: I/Oを引き起こしているプロセスを特定する。**
```sh
iotop -b -n 3 -d 5   # 15秒間のI/O消費トップ
pidstat -d 1 5       # プロセスごとのI/O統計
```

**ステップ4: 同期書き込みを確認する。**
同期書き込み（`O_SYNC`、`fsync()`、`fdatasync()`）はI/O stallの一般的な原因。アプリケーションが強制syncしているか確認：
```sh
# プロセスごとのfsync呼び出しを追跡
strace -e trace=fsync,fdatasync -p <pid> 2>&1 | head -20
```

**ステップ5: 書き込みパスを確認する。**
```sh
vmstat 1 5
# bo（毎秒書き込みブロック数）とbi（毎秒読み込みブロック数）を見る
# boが常に高い場合、vm.dirty_ratio閾値を確認
cat /proc/vmstat | grep -E 'nr_dirty|nr_writeback'
```

## よくある間違い

**top/vmstatの `%iowait` をPSIの代替として使う。** `%iowait` はCPUごとの指標で、マルチコアシステムでは誤解を招く。16コアマシンで1CPUが100%iowaitでも平均では6.25%にしか見えない。`io_some_avg10` にそのような希釈はない。

**`io_full_avg10` を無視する。** 多くのエンジニアは `io_some_avg10` しか見ない。`full` 指標が本当のダメージを示す。フルstallはストレージデバイスがシステムの全スループットを制御することを意味する——アプリケーションはI/OとCPU処理を全くオーバーラップできない。

**ストレージの問題のときにアプリケーションを責める。** `io_some_avg10` が高い時、アプリケーションレベルのタイムアウトは症状であって原因ではない。まずストレージのボトルネックを修正する; デバイスが飽和しているとアプリケーションのチューニングは効かない。

**NVMeとHDDを閾値で同一視する。** NVMeはキュー深さが大きいため `io_some_avg10` が高くても許容レイテンシを維持できることが多い。HDDで20%のio_someは、NVMeで20%よりはるかに危険。

**cgroupレベルで確認しない。** コンテナでは `/sys/fs/cgroup/io.pressure` がコンテナごとのI/O圧力を示す。cgroupにI/O制限が設定されていれば、システムレベルの値が正常でもあるコンテナが高い `io_some_avg10` を示すことがある。

## 関連項目

- `pressure.io_full_avg10` — I/O待ちで全タスクが同時にstall（危機的）
- `pressure.io_some_avg60` — トレンド確認のための1分間表示
- `diskstats.read_wait_distribution` — デバイスごとのI/Oレイテンシ分布
- `vmstat.nr_dirty` — writebackのI/Oストームを引き起こすdirtyページ蓄積
- `pressure.memory_some_avg10` — メモリ圧力、スワップ起因I/O中にしばしば同時発生
