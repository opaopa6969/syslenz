## この source の役割
`pressure` はプロトコル層のテレメトリ面です。ソケット挙動、パケットの進行、ユーザー体感遅延を接続して読むために使います。

## 運用エピソード
CPU・メモリは健全でも、この source のプロトコルカウンタが再試行や状態遷移異常を示し、断続タイムアウトの説明になったケースがありました。

## 読み方
1. 安定しやすい基線カウンタから始める。
2. 負荷スパイク時に先行して動くカウンタを特定する。
3. `ss` / conntrack / pressure とトレンドを照合する。
4. カウンタ変動を接続ライフサイクル段階に対応づける。

## パターン集
- 健全: トラフィック比例で増え、収束も速い。
- 警戒: トラフィック増加と独立に特定エラー/再試行が伸びる。
- 重大: 複数エラーパスが同時上昇し、正常進行が停滞する。

## 推奨ワークフロー
1. 最初の異常時刻を刻む。
2. ソケット層1つ・圧力層1つを必ずクロスチェックする。
3. 緩和策（レート制御、タイムアウト調整、リトライ方針）を選ぶ。
4. 再発時に使える証拠連鎖を残す。

- process / syscall / scheduler / memory / I/O / interrupt の層で捉える。
- この field がどの層の副作用かを先に固定する。
- 隣接 field 1つと跨層 field 1つで検証する。

## システム叙述（メモリ）

このシグナル（sourceguide.pressure）は単なる数字ではなく、カーネル状態遷移の露出面です。
この source は跨層の証拠連鎖に組み込むと信頼性が大きく上がります。

### エピソード: ダッシュボードの安心感とユーザー痛みがずれた日（メモリ）
- メモリ平均値は正常で、ダッシュボードは緑でした。
- しかしユーザー遅延はメモリバースト窓だけで悪化しました。
- このメモリ field が先に動き、隣接 field が方向を裏付けました。
- 勝ち筋は大きなメモリ調整ではなく、不確実性を素早く狭めることでした。

### 跨層翻訳（メモリ）
1. field の動きを、起こり得るカーネル経路に翻訳する。
2. 壁時計時間の損失が scheduler 遅延か I/O wait かを検証する。
3. 需要増とサービス時間増を分離する。
4. 変更後に症状と機序の両方で回復を確認する。

### Unix内部との接続（メモリ）
- process model（メモリ視点）: runnable が増えたのか、blocked が滞留したのか。
- syscall lifecycle（メモリ視点）: request時間は entry/sleep/wakeup/return のどこへ移ったか。
- interrupt path（メモリ視点）: wakeup配送や softirq backlog が tail を押し上げたか。
- scheduler（メモリ視点）: fairness は throughput を守りつつ tail を悪化させていないか。
