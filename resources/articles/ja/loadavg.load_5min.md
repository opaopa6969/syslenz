# load_5min

[English version](../en/loadavg.load_5min.md)

---

## これは何？

`load_5min` は、Linuxのロードアベレージの5分間指数移動平均です。`load_1min` と同じ「実行中＋I/O待ちプロセス数」を計測しますが、より長い窓で平滑化されています。`/proc/loadavg` の2番目のフィールドです。

`load_1min` が今この瞬間のスピードメーターなら、`load_5min` は直近の区間の平均速度です。短い渋滞はあまり反映されず、持続的な混雑が浮かび上がります。

```
  load_1min  ████████████░░░░░░  (反応が速い——スパイクが見える)
  load_5min  ██████████░░░░░░░░  (滑らか——トレンドが見える)
  load_15min █████████░░░░░░░░░  (最も遅い——ベースラインが見える)
              0         時間 →
```

3つの値の中で運用上最も有用なのがこの5分値です。本当の問題に反応するのに十分な速さを持ちながら、無害な1分スパイクをフィルタリングできる安定さもあります。

---

## なぜ重要？

`load_5min` の真の力は3つの値を一緒に読んだときに現れます。値同士の関係が、15分待たずに「悪化中か回復中か」を教えてくれます。

**トレンドのルール:**
- `load_1min > load_15min`: loadが**増加中**——スパイクは最近始まった
- `load_1min ≈ load_15min`: loadが**安定**——この状態がしばらく続いている
- `load_1min < load_15min`: loadが**減少中**——最悪期は過ぎた可能性が高い

だからオペレーターは3つを同時に眺めます。数値そのものより、その関係性が重要です。

**シナリオ:** 02:00にload=12のアラートが発火（8コアマシン）。確認すると:
```
load average: 12.3, 4.1, 1.8
```
これは「直近数分でloadが爆発した」という意味。02:00に何が始まったか確認する——cronジョブ、デプロイ、トラフィックスパイク。

一方これだと:
```
load average: 12.1, 11.9, 12.2
```
「15分間ずっとload=12だった」という意味。アラートが遅延していたのかもしれない。20分以上前に始まった何かを探す。

## 読み方

```sh
uptime
# load average: 5.20, 3.87, 2.41
#               1分   5分   15分
```

**一目でトレンドを読む:**

| 1分  | 5分  | 15分 | 解釈 |
|------|------|------|------|
| 8.0  | 4.0  | 2.0  | 急速に悪化中——今すぐ対応 |
| 4.0  | 4.0  | 4.0  | 安定した高負荷——この状態が続いている |
| 2.0  | 5.0  | 8.0  | 回復中——待てば収まる可能性あり |
| 0.5  | 3.0  | 6.0  | 急速回復——インシデントは終わりかけ |

**loadが本物かを確認する:**
```sh
# 30秒かけてloadトレンドを見る
watch -n 5 uptime

# vmstatでCPUかI/Oかを確認する
vmstat 1 5
```

## 実際のエピソード

データベースサーバーがload=24でアラートを発火した（12コア）。オンコールエンジニアがアラートから8分後に確認すると：

```
load average: 24.1, 22.8, 8.3
```

5分値（22.8）が1分値（24.1）に近いことから、「状況は新しくない——到着前から少なくとも5分間続いている」と分かった。15分値（8.3）から「問題は10〜15分前頃に始まった」と推定できた。最近のデプロイを確認すると、12分前にインデックスなしのフルテーブルスキャンをするマイグレーションジョブが走り始めていた。ジョブをkillして5分後：

```
load average: 4.2, 18.1, 12.5
```

load_1minの低下が「修正は効いている」を証明した。load_5minが追いつくにはもう数分かかる。数値から「回復が進んでいる」と確信でき、待つ必要はなかった。

**教訓:** 3つの値が合わさってタイムラインを形成する。1minが落ちても5minがまだ高い——それは「回復は始まったが完了していない」というサインだ。

## load_5minが持続的に高い時にやること

「持続的」とは、load_5minが5分以上高いままであること。これにより無害な1分スパイクは除外される。

**ステップ1: 3つの値を比較する。**
```sh
uptime
```
loadがまだ上昇中（1min > 5min）か、安定か、回復中かを判定する。

**ステップ2: loadの種類を確認する。**
```sh
vmstat 1 3
# wa列: 高い = I/O律速
# r列: 高い = CPU律速、b列: 高い = I/Oでブロック中
```

**ステップ3: タイムラインから原因を探す。**
`load_1min` と `load_15min` の差が「問題がいつ始まったか」のヒントになる。両者が等しければ、15分以上前から続いている。

```sh
# 最近の変化を確認
journalctl --since "15 minutes ago" | tail -50
last -n 10   # 最近のログイン
```

**ステップ4: トレンドが悪化中なら、チューニング前に原因を切り離す。**
上昇中のloadの下でチューニングしない。まずloadの原因になっているプロセスやジョブを分離する。

---

## よくある間違い

**load_5minを確認せずにload_1minだけに反応する。** 1分スパイクは多くの場合無害。エスカレーションの前にload_5minで確認を待つ。

**load_5minは遅れることを忘れる。** 問題を修正してもload_5minが下がるには数分かかる。すぐに値が下がらなくても修正が失敗したと思わない。

**トレンド方向なしに数値を読む。** 8コアマシンでload=6は、それが上昇中か下降中かを知らなければ何も意味しない。3値の広がりがシグナルだ。

**コア数が異なるマシンで同じ閾値でアラートする。** 常にコア数で正規化する: `load_5min / nproc > 1.5` の方がポータブルな閾値になる。

## 関連項目

- `loadavg.load_1min` — 瞬間的な表示、より反応が速い
- `loadavg.load_15min` — 最もゆっくり変化するベースライン値
- `stat.cpu_iowait` — loadのI/O対CPU性質を確認する
- `pressure.cpu_some_avg10` — PSIベースのCPU圧力（ロードアベレージより精密）
- `stat.procs_blocked` — ブロック中プロセスの直接カウント
