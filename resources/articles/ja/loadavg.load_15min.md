# load_15min

[English version](../en/loadavg.load_15min.md)

---

## これは何？

`load_15min` は、Linuxのロードアベレージの15分間指数移動平均で、`/proc/loadavg` の3つの値の中で最もゆっくり変化するものです。3番目のフィールドです。

`load_1min` が今の心拍、`load_5min` が直近のトレンドなら、`load_15min` はベースラインです。「このシステムにとっての今の正常」を教えてくれます。

```
  突発スパイクと回復:                     持続的な過負荷:
  ▲                                     ▲
  │      /\                             │           ___________
  │     /  \    load_1min              │          /
  │    /    \__  load_5min             │         /
  │___/______\___ load_15min           │________/   load_15minがゆっくり上昇
  └───────────────────────▶ 時間       └─────────────────────────▶ 時間
```

長い平滑化窓のため、`load_15min` はゆっくり変化します。3分だけ続いた突発的な問題ではほとんど動きません。20分続く問題なら目に見えて動きます。

---

## なぜ重要？

`load_15min` は「インシデントの中にいるのか、それともノイズを眺めているだけなのか」を教えてくれる数値です。

**ベースラインとして:** 健全なシステムでは `load_15min` が典型的なワークロードを反映します。健全な日に2.0で安定しているなら、2.0があなたのベースライン。`load_1min` が6.0にスパイクしても一時的かもしれない。`load_15min` が6.0なら、直近15分のほとんどがその水準にある——それはインシデントです。

**回復シグナルとして:** 問題を修正すると、まず `load_1min` が下がります。次に `load_5min`。`load_15min` は最後に追いつきます。`load_1min` が正常に戻っても `load_15min` がまだ高いなら、インシデントは終わったばかりで15分平均が追いつくのを見ている状態です。

**ドリフト検出器として:** `load_15min` が数日・数週間かけてじわじわ上がっていく——1.5→2.5→3.5——インシデントなしに。これはメモリリーク、暴走cronジョブ、やがてインシデントになる容量問題のサインであることが多い。

## 読み方

```sh
uptime
# load average: 1.20, 2.85, 5.40
#               ↑     ↑     ↑
#               1分   5分   15分
```

この出力は具体的なストーリーを語っています: しばらくload=5.4が続いていたが、今は急速に下がっている。load_1minが1.2なので、重い時期は最近終わった。回復は順調に進んでいる。

**方向性マトリクス:**

| 状態 | 意味 |
|------|------|
| 1min > 5min > 15min | 加速中——loadが上昇し続けている |
| 1min < 5min < 15min | 減速中——loadが下降、回復中 |
| 1min ≈ 5min ≈ 15min | 安定——その水準がずっと続いている |
| 1min >> 15min | 突発スパイク——急速回復か継続上昇かを注視 |
| 1min << 15min | 突発低下——インシデントが直近で解決した |

**この15min値はこのマシンにとって異常か？**
```sh
# 通常時のload_15minの挙動を把握する
sar -q 1 0   # sysstatsがインストールされていれば——時系列でloadを表示
```

## 実際のエピソード

決済処理サーバーが数ヶ月間 `load_15min` ≈ 1.5 で安定して動いていた。ある月曜日の朝、エンジニアが「過去2週間で3.8まで上昇していた」ことに気づいた——インシデントなし、アラートなし、ただのゆっくりとした上昇。

調査すると、6週間前に追加されたバッチレポートジョブが1時間ごとに巨大化するテーブルを再スキャンしていた。追加時の10倍にテーブルが成長。ジョブは最初4分で終わっていたが、今は1回22分かかり、次の実行と重なってどんどん積み上がっていた。

何も「壊れていなかった」——しかし15分平均が1分値のノイズに埋もれていたドリフトを示していた。インデックスを追加し、バックログが解消された数日後に `load_15min` は1.6に戻った。

**教訓:** 数日・数週間にわたる `load_15min` のゆっくりしたドリフトは、単発のスパイクよりも診断的なことが多い。

## load_15minが高い時にやること

`load_15min` が高いということは、過負荷がスパイクではなく持続していることを意味します。

**ステップ1: トレンドの方向を確認する。**
```sh
uptime
```
1min > 15minならまだ悪化中。1min < 15minならピークは過ぎた。

**ステップ2: loadがどれくらい続いているかを探る。**
`load_15min` が通常のベースラインを大きく上回っているなら、問題は15分以上続いている。もっと前を確認する:
```sh
journalctl --since "30 minutes ago" | grep -i "error\|warn\|fail"
```

**ステップ3: loadの種類を確認する。**
```sh
vmstat 1 3
# I/O律速: wa高、b高、r低
# CPU律速: wa低、r高
```

**ステップ4: 修正後は、ゆっくりした回復を見守る。**
`load_15min` が修正を反映するまで10〜15分かかる。焦らない。まず `load_1min` で回復を確認し、その後 `load_15min` が下降トレンドに入るのを見守る。

## よくある間違い

**素早いインシデントを検知するために `load_15min` を使う。** これには遅すぎる。突発スパイクのアラートは `load_1min` を使う。`load_15min` は持続的な問題の確認やゆっくりしたドリフトの検出に使う。

**`load_15min` がまだ高いのに「回復した」と宣言する。** 15分平均は遅行指標。5分前に問題を解決しても、`load_15min` はさらに10分間高い値を示し続ける。回復の確認には `load_1min` を使う。

**数日かけてのゆっくりしたドリフトを無視する。** ほとんどの監視は閾値越えに焦点を当てる。閾値以下に留まる緩やかな `load_15min` ドリフトはほとんどの監視システムには見えない。トレンドベースのアラートや週次レビューを検討する。
