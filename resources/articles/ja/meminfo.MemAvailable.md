# MemAvailable

[English version](../en/meminfo.MemAvailable.md)

---

## これは何？

`MemAvailable` は、スワップを使わずに新しいアプリケーションを起動できるメモリ量のカーネル推定値です。カーネル3.14で追加され、`MemFree` が答えられない問いに答えます：「今実際にどれだけメモリを使えるか？」

重要なのは、Linuxがファイルキャッシュを使い捨て可能なものとして扱うことです。プロセスがメモリを必要とすると、カーネルはキャッシュページをその場で回収できます。つまりキャッシュは「使われている」とは言えません。`MemAvailable` = 空きメモリ + 回収可能なキャッシュ + 回収可能なスラブ。

```
  総RAM: 16 GB
  ┌──────────────────────────────────────────┐
  │ アプリメモリ (AnonPages)  4 GB  ← 固定  │
  │ ファイルキャッシュ(Cached) 8 GB  ← 回収可能
  │ カーネル/スラブ            1 GB  ← 一部回収可能
  │ MemFree                   3 GB  ← 純粋な空き
  └──────────────────────────────────────────┘
                              ↑
  MemAvailable ≈ 3 + 8 + 0.5 ≈ 11 GB
```

---

## なぜ重要？

**MemAvailableは日常監視で最も役立つメモリ健全性指標です。** 低下すると：

- **MemTotal の約20%以下**：スワップ圧力が始まります。カーネルはスペース確保のため匿名ページをスワップへ移し始めます。
- **約5%以下**：OOMキラーが発動しやすくなります。予期しないプロセスが殺されることもあります。
- **0**：カーネルが危機的状態。新規割り当てが失敗し、システムは無反応になります。

低下はしばしば緩やかで無音です。10 MB/時間でメモリをリークするアプリは、手遅れになるまで何時間もアラートを出しません。

## 読み方

```sh
# クイックチェック — 健全か？
free -h
# "available" 列を見る（"free" ではない）

# 経過観察
watch -n 5 'grep -E "MemAvailable|MemTotal|SwapFree" /proc/meminfo'

# パーセンテージで確認
awk '/MemAvailable/{a=$2} /MemTotal/{t=$2} END{printf "%.1f%%\n", a/t*100}' /proc/meminfo
```

| MemAvailable / MemTotal | 状態 |
|-------------------------|------|
| > 40% | 健全 |
| 20〜40% | トレンドを監視 |
| 10〜20% | 圧力上昇 — 調査を |
| < 10% | 危険 — 即対応 |
| < 5% | OOM間近 |

**アラート閾値の目安**：15%未満で警告、5%未満でページング。

## 実際のエピソード

火曜日の午前3時のことです。Node.jsアプリがセッションキャッシュをメモリ内で管理していました。ユーザーがログインするたびに数KBのJSONが保存されます。負荷は何ヶ月もかけてゆっくり増えていました。誰も気づいていませんでした——セッションの有効期限が壊れていて、セッションが一切削除されなかったのです。

午前2時47分、`MemAvailable` が4%に達しました。カーネルは匿名ページをスワップし始めました。レスポンスタイムは50msから4秒に跳ね上がりました。午前3時02分、OOMキラーが発動し、Node.jsアプリではなくデータベースのサイドカーを殺しました——その瞬間RSSが最も高かったのがサイドカーだったからです。

オンコールのエンジニアが目を覚ますと「データベース接続拒否」のアラートが届いていました。「メモリ不足」のアラートではなく。彼らは45分間、見当違いのデバッグをしました。

教訓：`MemAvailable` を `MemTotal` に対するパーセンテージで監視し、危機的になる前にアラート閾値を設定してください。OOMキラーに問題を教えてもらうのでは遅すぎます。

## 低い時にやること

**ステップ1：圧力を数値化する。**
```sh
awk '/MemAvailable/{a=$2} /MemTotal/{t=$2} END{printf "%.1f%%\n", a/t*100}' /proc/meminfo
```

**ステップ2：スワップが使われているか確認する。**
```sh
grep SwapFree /proc/meminfo
# 実際のスワップ活動も確認：
vmstat 1 5 | awk '{print $7, $8}'  # si（スワップイン）と so（スワップアウト）
```
`so` がゼロ以外なら、今まさにスワップが行われています——それが今払っているレイテンシです。

**ステップ3：誰がメモリを消費しているか。**
```sh
# RSS順のメモリ消費上位
ps aux --sort=-%mem | head -20

# AnonPagesが高いか確認（本物のアプリメモリ）
grep AnonPages /proc/meminfo
```

`AnonPages` が大きく増加中なら、アプリケーションがリークしているか解放していません。`Cached` が大きければ、カーネルが自動的に回収する可能性があります——ただしステップ2で確認してください。

**ステップ4：キャッシュを強制解放する（非破壊的、テスト目的のみ）。**
```sh
sync && echo 3 > /proc/sys/vm/drop_caches
# ページキャッシュ＋dentry＋inodeを解放。MemAvailableが一時的に跳ね上がる。
# 本番で定常的に行ってはいけない——パフォーマンスが悪化する。
```

**ステップ5：リークが確認されたら、リークしているサービスを再起動する**か、ホストにメモリを追加してください。カーネルチューニングはリークを直しません。

## よくある間違い

**`MemFree` を見て `MemAvailable` を見ない。** `MemFree` は忙しいLinuxサーバーでほぼ常に低い値です。重要なのは `MemAvailable` です。

**キャッシュが大きくてパニックになる。** `Cached` がRAMの60%を占めているのは健全です——ファイルシステムキャッシュが活躍しているということです。`Cached` ではなく `MemAvailable` を確認してください。

**絶対値でアラートを設定する。** 「MemAvailable < 1 GB」のアラートは4GBホストでは意味がなく、512GBホストでは過剰です。常にパーセンテージを使ってください。

**トレンドを無視する。** 1回の低い読み取りはバーストかもしれません。何時間も着実に下がり続ける `MemAvailable` はリークです。時系列ビューを使ってください。

**間違ったプロセスを再起動する。** OOMキラーは「コストが最も高い」犠牲者を選ぶのであって、原因を選ぶわけではありません。`ps` や `/proc/<pid>/status` で実際のリーカーを見つけてください。

## 関連項目

- `meminfo.MemFree` — 純粋な空きページ（通常は監視すべき指標ではない）
- `meminfo.Cached` — MemAvailableの大部分を構成するファイルキャッシュ
- `meminfo.AnonPages` — アプリのヒープ/スタック；ここが増えているなら本当に消費している
- `meminfo.SwapFree` — スワップ余力；MemAvailableと同時に低下したら危険
- `pressure/memory_some_avg10` — カーネルレベルのメモリストールシグナル
