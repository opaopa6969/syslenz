## なぜ /proc 読解に効くか
`/proc` の多くはプロセスライフサイクルの副作用を切り取った値です。`fork -> exec -> wait` を理解すると、カウンタは単なる数字ではなく実行の物語になります。

## メンタルモデル
- `fork`: プロセス状態の複製（現代カーネルでは COW で比較的軽量）。
- `exec`: プロセスイメージを新しいプログラムへ置換。
- `wait`: 親が子の終了状態を回収し、ゾンビ化を防ぐ。

運用障害では「単一値」より、3段階の比率崩れとして現れることが多いです。

## エピソード: 「CPUは余裕なのに全体が遅い」
CPU 50% 未満でも遅延が急増したケース。
- `process_count` と `forks_total` が急上昇。
- `runqueue` は高いが飽和までは行かない。
- ログには短命ワーカー再起動が多発。

真因は計算不足ではなく、`fork/exec` ストームでした。

## syslenzで見る場所
1. `stat.process_count` と `stat.forks_total` の推移。
2. スケジューラ系（`schedstat.*`、runqueue 分布）。
3. churn 連動のメモリ副作用（page fault、reclaim）。
4. プロセス生成がカーネル仕事を増やす場合の context switch / softirq。

## 誤読しやすい点
- 「CPU低い=健全」: churn 主因では成立しない。
- 「load高い=CPU不足」: ブロック待ちや起動ストームかもしれない。
- 「process数増加=リーク」: ロールアウト挙動の可能性もある。

## 深掘りメモ
- `fork` の主コストはメモリコピーよりページテーブル/TLB 側へ寄る。
- `exec` コストはバイナリサイズ、動的リンク、FS キャッシュで変動。
- orphan/zombie は CPU 顕在化なしにカウンタを歪める。
