# memory_some_avg10

[English version](../en/pressure.memory_some_avg10.md)

---

## これは何？

`memory_some_avg10` は、直近10秒間のうち、少なくとも1つのタスクがメモリを待ってstallしていた時間の割合を計測します——カーネルがページを回収中、スワップI/Oを待っている、またはすぐに完了できないメモリ割り当てを処理中で、プロセスが進めなかった時間です。

カーネル4.20から利用可能なLinux PSI（Pressure Stall Information）の一部で、`/proc/pressure/memory` から読み取られます。

```
  メモリstallの仕組み:

  プロセスがメモリを確保しようとする
         |
         v
  カーネル: 「先にページを回収する必要がある」
         |
         v
  プロセスがBLOCK——これがmemory_some_avg10にカウントされる
         |
         v
  カーネルがページを解放（キャッシュを追い出す、スワップから読む）
         |
         v
  プロセスが続行

  memory_some_avg10 = 上の「BLOCKされた」ステップに費やした時間の%
```

**MemAvailableより重要な理由:** `MemAvailable` は空きメモリの量を教えてくれます。`memory_some_avg10` はプロセスが実際にメモリ圧力による遅延を経験しているかどうかを教えてくれます。MemAvailableが2GBあっても、カーネルがかろうじて入るワーキングセットのためにキャッシュページを常に回収していれば `memory_some_avg10=25%` になります。

---

## なぜ重要？

メモリ圧力は診断が最も難しい問題の一つです。なぜなら、明らかなメモリ枯渇なしに謎のレイテンシとして現れることが多いからです。`memory_some_avg10` はそのギャップを埋めます。

**シナリオA——見えない殺し屋:** あるサービスがメモリ利用率60%、MemAvailableは4GB空き。しかしp99レイテンシが30秒ごとにスパイク。誰もメモリを疑わない。`memory_some_avg10` は18%: ワーキングセットがかろうじてRAMに入っており、新しい割り当てが来るたびにカーネルがLRUページを懸命に回収している。

**シナリオB——スワップの盲点:** スワップが有効なマシン。MemAvailableは512MB。スワップは目に見えていない。しかし `memory_some_avg10` は45%、`memory_full_avg10` は12%（全タスクがstall）。MemAvailableもスワップ使用量も明らかにしない深刻なメモリ問題が進行中。

**cgroupレベルの可視性:** コンテナ環境では、`/sys/fs/cgroup/memory.pressure` で個々のコンテナのPSIが分かります。ノードが健全に見えても、あるポッドがメモリstallを経験していることがあります。

## 読み方

```sh
cat /proc/pressure/memory
# some avg10=3.21 avg60=2.87 avg300=1.54 total=34567890
# full avg10=0.12 avg60=0.08 avg300=0.03 total=789012
```

**`some` vs `full`:**
- `some`（memory_some_avg10）: 少なくとも1つのタスクがメモリを待ってstall。他のタスクは通常動ける。メモリ圧力が存在することを示す。
- `full`（memory_full_avg10）: すべての非アイドルタスクが同時にstall。全プロセスがメモリを待つ間CPUはアイドル。深刻——システムはほぼ使用不能。

`full` が1〜2%を超えたら深刻なアラーム。`some` は一部のワークロードでは10%まで許容できます。

**実用的な閾値:**

| memory_some_avg10 | 解釈 |
|---|---|
| 0 – 2% | 健全 |
| 2 – 10% | 軽度の圧力——監視する価値あり |
| 10 – 25% | 中程度——レイテンシへの影響が出やすい、MemAvailableとスワップを確認 |
| > 25% | 高い——重大なstall時間、reclaim を調査 |
| > 50% | 危機的——システムが苦しんでいる、OOMリスクあり |

## 実際のエピソード

機械学習推論サービスが定期的なレイテンシスパイクに悩まされていた——2〜3分ごとに、p99レイテンシが約10秒間80msから600msに跳ね上がる。メモリ利用率アラートは90%に設定されており、マシンは72%。何もトリガーしなかった。

エンジニアがシンプルな監視ループを設定：
```sh
while true; do
  date
  cat /proc/pressure/memory
  sleep 5
done
```

出力は `memory_some_avg10` が0.5%（正常）と28〜35%（スパイク時）の間で振動していることを示した。スパイクはレイテンシイベントと完全に一致。

さらなる調査: 推論モデルは3.2GBのモデルウェイトを循環的にアクセスするホットアクセスパターンを持っていた。マシンは8GB RAMだが他の複数のサービスも動いていた。このサービスに実質的に利用可能なRAMは約2.8GB。2分ごとにカーネルが別サービスの割り当てのためにモデルウェイトをページキャッシュから追い出し、モデルが再度そのウェイトにアクセスするたびにメジャーページフォルトとメモリ回収が発生していた。

修正: `mlock()` でモデルウェイトをメモリに固定し、競合サービスのメモリ制限を設定。レイテンシスパイクが消えた。

**教訓:** `memory_some_avg10` は、MemAvailableや利用率パーセンテージが完全に見逃すメモリ起因のレイテンシを特定できる。

## 高い時にやること

**ステップ1: `some` と合わせて `full` も確認する。**
```sh
cat /proc/pressure/memory
```
`full_avg10` > 2%なら危機的として扱う。`some` だけが高いなら、まだ余裕がある。

**ステップ2: MemAvailableとスワップを確認する。**
```sh
free -h
vmstat 1 5   # si/so列: スワップイン/アウト毎秒
```
スワップ活動なしに `memory_some_avg10` が高い = ページキャッシュでreclaim発生（ファイルバックページを追い出し）。スワップI/Oが高い = キャッシュを超えてスワップに踏み込んでいる。

**ステップ3: 誰がメモリを消費しているかを探す。**
```sh
ps aux --sort=-%mem | head -20
# cgroupの場合:
cat /sys/fs/cgroup/*/memory.current 2>/dev/null | sort -rn | head -10
```

**ステップ4: ページ回収活動を確認する。**
```sh
vmstat 1 5
# si/so（スワップ）とbi/bo（ブロックI/O）を見る
# 明らかなI/OワークロードなしにbiがI高 = スワップかディスクからのpage reclaim
```

**ステップ5: メモリ追加またはlimit調整を検討する。**
reclaim が常時発生して避けられないなら、ワーキングセットが入りきっていない。RAM追加、他サービスのメモリ制限削減、またはワーキングセットの削減を検討する。

## よくある間違い

**MemFreeや利用率パーセンテージだけにメモリアラートを設定する。** これらの指標はメモリがどれだけ使われているかを教えるが、プロセスが影響を受けているかどうかは教えない。忙しいカーネルは70%利用率でもプロセスをstallさせることがある。

**`memory_full_avg10` を無視する。** `some` 指標は警告。`full` 指標は緊急事態。`full` を確認しないと、システムがほぼ使用不能な状態に傾くのを見逃す可能性がある。

**PSIを確認せずにネットワークやアプリケーションのバグにレイテンシスパイクを帰因する。** メモリ起因のレイテンシは外から見るとネットワークレイテンシとそっくり。パケットキャプチャを開く前に `memory_some_avg10` を確認する。

**スワップ = メモリ圧力と思い込む。** スワップが無効なシステムでも深刻なメモリ圧力が起こる（すべてのreclaim がページキャッシュから）。積極的にスワップしているシステムが、ページキャッシュをスラッシングしているシステムより `memory_some_avg10` が低いこともある。PSIは機構ではなく実際のstallを計測する。

## 関連項目

- `pressure.memory_full_avg10` — すべてのタスクがstall（危機的な閾値）
- `pressure.memory_some_avg60` — トレンド確認のための1分間表示
- `meminfo.MemAvailable` — 利用可能メモリの推定値（PSIの補完）
- `vmstat.pgmajfault` — メジャーページフォルト、メモリstallとよく相関する
- `pressure.io_some_avg10` — I/O圧力、スワップ中のメモリ圧力としばしば同時発生
