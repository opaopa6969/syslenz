# conntrack 分布

## NAME
`conntrack.conntrack_distribution` - conntrack テーブルの件数とヘッドルームを横断して読むグループ記事

## なぜ今読むか
リトライやドロップ、タイムアウトの嵐が単一カウンタと一致しないときにこのグループを開きます。`conntrack_count` が `conntrack_max` に迫りつつ、`usage_pct` が揺れるとき、分布として構造的に証明する必要があります。

## 証拠の順序
1. 症状の窓（タイムアウト、レート制限、SYN ドロップ）を記録し、ユーザー影響を固定する。
2. `conntrack_count` のトレンドと `conntrack_max` までの距離を確認する。
3. 短命セッションのチャーンか長寿命セッションの蓄積かを見極める。
4. タイムアウト、cgroup の制限、NIC オフロードなどを使って可逆的にヘッドルームを増やし、クロスレイヤーで回復を確認する。

## 分布コンポーネント
- **conntrack_count**: 現在追跡している接続数。新規フローが掃除を上回ると直線的に増える。
- **conntrack_max**: カーネルに設定された上限。固定値なら静的深さ、伸長中なら意図的なヘッドルーム。
- **conntrack.usage_pct**: 長期的な max との比率でノイズを除き、継続的なドリフトをとらえる。

## 運用語り
conntrack テーブルはカーネルと NAT ヘルパー、接続指向のワークロードが共有する資源です。短命セッションが増えると `conntrack_count` が爆上げし、`conntrack_max` は平行線のまま、`usage_pct` が閾値を越える事故が定番です。チームは cleanup に追いつかずにタイムアウトで終了するか、テーブルが満杯になって SYN ドロップを出すかのどちらか。正解は単一カウンタやヘッドルームではなく、分布を語ることです。

## 読み方
1. `conntrack_count` と `conntrack.usage_pct` をトレンドで見て、傾きと揺れを俯瞰する。
2. `conntrack_max` のラインを重ね、残りヘッドルームがどれだけかを把握する。
3. `net/snmp.Tcp_SynDropped` や `net/stat` の状態遷移と相関させて説明力を上げる。
4. `usage_pct` によって一時的なバーストをフィルタし、持続的なドリフトに集中する。

## 判断シグナル
- **低リスク**: クライアント負荷と比例した上昇で、バースト後に即座に戻る。
- **警戒**: usage_pct が 80% 以上を繰り返すが症状が治まらない。
- **重大**: `conntrack_count == conntrack_max` で `TCPSynRetrans` や `usage_pct` が飽和する。

## 誤読パターン
- なぜカウントが増えたのか（容量 vs リーク）を確認せずに `conntrack_max` を上げる。
- 合法的なバッチが引き起こしたスパイクを異常と見なす（リクエストタイムラインで確認）。
- チェックサムオフロードや NAT ヘルパーを切るときに、分布自体を参照しない。

## 行動ループ
1. 短命チャーンか粘着セッションか仮説を立てる。
2. 制限を一時的に緩めて（`conntrack -F`、タイムアウト延長）、状態を解放する。
3. 変更後に `conntrack_count` と `usage_pct` の傾きを再測定する。
4. 次の事件のために証拠チェーンを記録する。

## Unix内部システム視点
- **プロセス層**: ソケットペアごとに状態が増え、ヘルパーが保持すると掃除が遅れる。
- **システムコール層**: accept/close のタイミングがカウントとエイジングキューを動かす。
- **スケジューラ視点**: backlog や softirq の遅延が `nf_conntrack` の掃除を後ろ倒しにし、ヘッドルーム喪失を増幅する。
- **I/O/割り込み**: VXLAN や GRO などのオフロードバーストが高パケットレートでテーブルを圧迫する。

## 演習
### Drill A: キャパシティ物語
1. 負荷テストのバースト窓を選ぶ。
2. 時系列に `conntrack_count`、`conntrack_max`、`usage_pct` を書き込む。
3. ドリフトが需要増か経時的な残滓かを説明する。

### Drill B: 可逆的な緩和
1. タイムアウトか max かブロックリストのどれかをゆるく緩める。
2. 失敗したときに戻せる guard（秒数や失敗パケット数）を添えて変更する。
3. 症状が治まらなければロールバックして指標を記録する。

### Drill C: 証拠圧縮
1. 症状、プライマリ、セカンダリ、行動、反応、結論を六行で書く。
2. チームと共有し、観測と一致するか確認する。

## クイックチェック
- 最初の conntrack 警告エントリのタイムスタンプ。
- 事件時の `conntrack_count` と `conntrack_max` の距離。
- cleanup やタイムアウトがワークロードに適合していたか。
- 実施したアクションとロールバック guard（例: `conntrack_max` バンプ + cleanup スクリプト）。
- 傾きや揺れが収束したことの確認。

## 障害フォレンジクス
### 証拠取得
- `conntrack_count` 対 `conntrack_max` グラフをイベント窓付きで保存。
- `net/snmp` の再送/ドロップ等も添えておく。

### 判断記録
- 主張: 単一カウンタではなく分布がスループットを制限していた。
- 反証: NIC 制限や他レイヤーが同じ筋書きを描けないか？
- 行動メモ: タイムアウト調整など可逆的な操作しかしていない。

## 失敗類型マトリクス
- **類型A**: cleanup 後もカウントが増え続け、容量をリークと誤認する。
- **類型B**: `conntrack_max` を無条件に増やし、ヘルパーのバックログにヘッドルームを残さない。
- **類型C**: usage_pct が100%なのに、それと無関係なファイアウォールルールを調整する。

## 反事実分岐
1. テーブルが大きければタイムアウトは改善しただろうか？ (`usage_pct` で推論)
2. cleanup が 500ms 遅れていたらどのメトリクスが最初に上がるか？ (`conntrack_count`)
3. 状態寿命を測れるなら、次にどのバケットをスロットルすべきか？
