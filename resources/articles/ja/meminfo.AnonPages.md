# AnonPages

[English version](../en/meminfo.AnonPages.md)

---

## これは何？

`AnonPages` は、アプリケーションのヒープ、スタック、プライベートメモリマップ領域——ディスク上のファイルに紐付かないあらゆるもの——が使っているメモリです。アプリケーションが `malloc()` を呼び出したり、Pythonオブジェクトを割り当てたり、ヒープを拡張したりすると、そのページがここに現れます。

「匿名（Anonymous）」とは、ページの背後にファイルがないことを意味します。カーネルがそれを回収する必要があっても、単純に破棄することはできません（ディスクのコピーが存在しない）——スワップに書き出すか、プロセスを殺すしかありません。

```
  ファイルキャッシュ（Cached）：
    アプリが /etc/config を読む → ディスクが背後にあるページ → 無料で追い出せる

  匿名ページ（AnonPages）：
    アプリが malloc(1MB) をする → 背後に何もないページ → 追い出せない
    （回収するにはスワップするかプロセスを殺すしかない）
```

`AnonPages` は、`/proc/meminfo` の中で「アプリケーションが実際に消費しているメモリ」に最も近い値です。

---

## なぜ重要？

**OOMキラーが実際に見ているものです。** メモリが尽きると、カーネルはスワップするか殺すしか匿名ページを回収できません。`AnonPages` が高いほど、カーネルの余裕がありません。

**メモリリーク検出器です。** リクエスト負荷が横ばいなのに `AnonPages` が何時間も着実に増えているなら、何かがリークしています。`Cached` は自然に変動しますが、`AnonPages` は安定した負荷では比較的安定しているはずです。

**MemAvailableの低下が本物かどうか判断できます。** `MemAvailable` が低下していて `AnonPages` も同じ速度で上昇しているなら、アプリケーションが本当により多くのメモリを消費しています。`MemAvailable` が低下しているのに `AnonPages` が安定しているなら、キャッシュの挙動が原因の可能性が高いです。

## 読み方

```sh
# AnonPages のトレンドを監視
watch -n 5 'grep -E "AnonPages|MemAvailable|SwapFree" /proc/meminfo'

# プロセスごとの匿名メモリ
cat /proc/<pid>/status | grep -E "VmRSS|VmAnon|RssAnon"

# 全プロセスをRSS順でソート
ps aux --sort=-%rss | head -20
```

**トレンドの解釈：**

| AnonPages の挙動 | 意味 |
|----------------|------|
| 安定 | 健全——アプリが安定したメモリを使用 |
| 何時間も緩やかに上昇 | リークの可能性——リクエスト数と照合 |
| 急速に上昇 | 負荷スパイクまたは暴走的な割り当て |
| 低下中 | アプリがメモリを解放、またはプロセスが終了 |

## 実際のエピソード

Pythonのウェブサービスが画像アップロードを処理していました。開発者は通常負荷下でメモリ使用量をプロファイルしていて、問題なさそうに見えていました。本番デプロイ後、`AnonPages` は1時間に200 MB増加し続けました。

チームは1日間 `MemAvailable` が低下するのを見ていましたが、誰もそのトレンドに気づきませんでした。その時点で `AnonPages` は2 GBから7 GBに増えていました。`ps` でプロセスごとのRSSを確認すると、ウェブワーカープロセスがすべて大量のメモリを保持していました。

犯人：PIL（Pillow）の画像オブジェクトが「パフォーマンスのため」にモジュールレベルの辞書にキャッシュされていました。キャッシュに退避ポリシーがありませんでした。通過する固有の画像サイズのたびに永続的なエントリが作られました。辞書は永遠に増え続けました。

修正：LRU退避付きの最大サイズキャッシュを追加。デプロイ後数分で `AnonPages` が安定しました。

教訓：安定した負荷で増え続ける `AnonPages` はリークです。スナップショットではなく、時系列でプロセスごとのRSS追跡で見つけてください。

## メモリリークの探し方

**ステップ1：負荷によるものでないことを確認する。**
```sh
# AnonPages の増加をリクエスト数と比較
# リクエストが横ばいでも AnonPages が増えるならリーク
grep AnonPages /proc/meminfo  # 数分ごとにサンプリング
```

**ステップ2：リークしているプロセスを見つける。**
```sh
# 全プロセスのRSSをスナップショット、10分待って再度スナップショット
ps -eo pid,comm,rss --sort=-rss | head -20
# どのプロセスが増えているか？
```

**ステップ3：/proc/<pid>/status で確認する。**
```sh
watch -n 30 'cat /proc/<pid>/status | grep -E "VmRSS|VmSize|RssAnon"'
```
`RssAnon` がそのプロセスの `AnonPages` カウントとほぼ一致します。

**ステップ4：リークしているプロセスをプロファイルする。**
インタープリタ言語（Python、Ruby、Node.js）は言語組み込みのヒーププロファイラを使います。C/C++は `valgrind --leak-check=full` または `heaptrack`。Goは `pprof`。

## よくある間違い

**`AnonPages` を総RSSと混同する。** プロセスのRSSには匿名ページとファイルに紐付くページ（共有ライブラリ、mmapされたファイル）の両方が含まれます。`/proc/<pid>/status` の `RssAnon` が純粋な匿名部分を示します。

**メモリ問題なのにキャッシュのせいにする。** `MemAvailable` が低くても `AnonPages` が小さければ、問題はキャッシュの挙動であってリークではありません。どちらかを確認してからサービスを再起動してください。

**スナップショット1回で判断する。** メモリリークはトレンドであって値ではありません。単発の `AnonPages = 5 GB` はコンテキストなしでは何も教えてくれません。

**スワップを無視する。** `AnonPages` が高くてスワップが使われているなら、アプリケーションは実質的にスローモーションで動いています。`vmstat` の `si`/`so` フィールドを確認してください。

## 関連項目

- `meminfo.MemAvailable` — 全体的なメモリ余力
- `meminfo.SwapFree` — AnonPagesが高い場合、スワップが安全網（そして遅い）
- `meminfo.Cached` — 回収可能なファイルに紐付くメモリ（AnonPagesと対比）
- `vmstat.pgpgout` — ディスクに書き出されたページ数（匿名ページのスワップアウトを含む）
