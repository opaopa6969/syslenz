# nr_dirty

[English version](../en/vmstat.nr_dirty.md)

---

## これは何？

`nr_dirty` は、メモリに書き込まれたがまだディスクにフラッシュされていないページ数です。カーネルは書き込みをまずRAMにバッファします。アプリがファイルに書き込むと、カーネルはそのページを「ダーティ」とマークし、バックグラウンドのカーネルスレッド（`pdflush` / `kworker`）が後でストレージに書き出します。

「未保存の作業」と考えてください。ダーティページはRAMにしか存在しないデータです。今システムがクラッシュしたら、そのデータは消えます。

```
  アプリがファイルに書き込む
       |
       v
  ページキャッシュ（RAM）   <-- nr_dirty がここを数える
  [ダーティ] [ダーティ] [ダーティ] [クリーン] [クリーン]
       |
       | pdflush / kworker がバックグラウンドでフラッシュ
       v
  ディスク（永続）         <-- nr_writeback がフラッシュ中を数える
```

---

## なぜ重要？

**書き込み圧力。** `nr_dirty` が上昇し続けると、カーネルはフラッシュが追いつかないほど書き込みを溜め込んでいます。最終的にカーネルはアプリケーションを抑制（ストール）して、バックログが解消されるまで待たせます。これが原因不明の書き込みレイテンシスパイクとして現れます。

**データ耐久性リスク。** ダーティページが多いほど、クラッシュや電源断でのデータ損失が増えます。多くのアプリは `fsync()` を使うので問題ありませんが、データベースやメッセージキューは大きく影響を受けます。

**フラッシュストーム。** `nr_dirty` がカーネルの `dirty_background_ratio` 閾値に達するとバックグラウンドフラッシュが始まり、`dirty_ratio` に達するとアプリの書き込みが直接ブロックされます。ダーティがゆっくり溜まって一気に放出されると、周期的なレイテンシスパイクが発生します。

```
  nr_dirty の時系列：

  ▲
  │         /\        /\
  │        /  \      /  \      <-- フラッシュストーム：バースト後に急落
  │       /    \    /    \
  │______/      \__/      \___
  └──────────────────────────▶ 時間

  健全な状態：
  ▲
  │ ~~~~~~~~~~~~~~~~~~~        <-- 低く安定、継続的にフラッシュ
  └──────────────────────────▶ 時間
```

## 読み方

**絶対値よりトレンドを見る。** 大量書き込みのサーバーがダーティページ50,000枚を常時持っていても正常です。ほぼ読み込み専用のワークロードで同じ値なら警戒信号です。

**`nr_writeback` と必ずセットで見る。** この2つが一緒にストーリーを語ります。

| 状況 | nr_dirty | nr_writeback | 意味 |
|------|----------|--------------|------|
| 通常の書き込み負荷 | 低〜中 | 低 | フラッシュが追いついている |
| 書き込みバースト | 上昇中 | 上昇中 | フラッシュ稼働中、抑制に注意 |
| 抑制リスク | 高く横ばい | 低 | フラッシュが止まっているか詰まっている |
| フラッシュストーム後 | 下降中 | 下降中 | 回復中 |
| ストレージボトルネック | 高 | 0 | 書き込み不能 — ディスク確認 |

**知っておくべきカーネル閾値：**

```
  /proc/sys/vm/dirty_background_ratio   （デフォルト: 10%）
  → RAM のこの割合を超えるとバックグラウンドフラッシュ開始

  /proc/sys/vm/dirty_ratio              （デフォルト: 20%）
  → この割合を下回るまでアプリの書き込みがブロック

  /proc/sys/vm/dirty_expire_centisecs   （デフォルト: 3000 = 30秒）
  → この時間より古いページは割合に関係なくフラッシュ
```

実際の値の確認：
```sh
sysctl vm.dirty_background_ratio vm.dirty_ratio vm.dirty_expire_centisecs
```

## 高い時にやること

**Step 1: 実際に問題が起きているか確認する。**
`pressure/io_some_avg10` を見てください。I/Oプレッシャーも高ければアプリが抑制されています。プレッシャーが低ければ、高いダーティ値は正常な書き込みバッファリングかもしれません。

**Step 2: フラッシュが動いているか確認する。**
```sh
cat /proc/vmstat | grep -E 'nr_dirty|nr_writeback'
# 5秒間隔で2回実行 — 数値が動いているか？
```
`nr_dirty` が高くて `nr_writeback` が0なら、フラッシュを阻んでいる何かがあります。ディスク健全性とI/Oエラーを確認してください：
```sh
dmesg | tail -20
iostat -x 1
```

**Step 3: writeback のスループットを確認する。**
`/proc/vmstat` の `nr_written` がディスクへの書き込みページ総数を数えます。`nr_dirty` が上昇しているのに `nr_written` が横ばいなら、フラッシュが完了していません。

**Step 4: 必要なら調整する。**
フラッシュストームがレイテンシに影響しているなら、ダーティ比率を下げてバーストを平坦化します：
```sh
# より積極的なバックグラウンドフラッシュ、バースト軽減
sysctl vm.dirty_background_ratio=5
sysctl vm.dirty_ratio=10
```
本番適用前に必ず計測してください — 比率を下げるとI/Oスループット要件が上がります。

---

## よくある間違い

**高い数値を自動的に悪いと判断する。** バルク書き込みをするデータベースは `nr_dirty` が高いのが普通です。問題は抑制（`dirty_ratio` 超過）やレイテンシが発生しているかどうかです。

**`nr_writeback` を無視する。** `nr_dirty` だけではフラッシュが健全かわかりません。100,000枚でwritebackが活発な状態と、100,000枚でwritebackがゼロな状態は全く意味が違います。

**`dirty_ratio` をスループット計測なしで調整する。** ダーティ比率を下げると、より頻繁に小さいフラッシュが発生します。SSDなら問題ありませんが、HDDでは頻繁なフラッシュがシーク負荷を増やします。

## 関連項目

- `vmstat.nr_writeback` — 現在ディスクに書き込み中のページ（フラッシュパイプライン）
- `vmstat.nr_dirty_threshold` — アプリストールが始まるカーネル計算済み上限
- `pressure/io_some_avg10` — I/Oプレッシャーが実際に感じられているか
- `diskstats` — デバイスごとの書き込みスループットとキュー深さ
