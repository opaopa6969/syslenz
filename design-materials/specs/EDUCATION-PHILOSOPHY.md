# syslenz 教育設計哲学

## 核心原則: 「知っていることで思考が広がる」

システム監視ツールを使う時、私たちは知っているパラメータだけを見る。600フィールドあっても、知らないフィールドは存在しないのと同じだ。エキスパートは、私たちが知りもしないパラメータから問題を調査する。これはレベルの問題であり、知識の問題だ。

**教育は syslenz のファーストクラス機能である。** 監視ツールではなく、教育プラットフォームとしての監視ツール。

## 3つの教訓

### 1. Unix man コマンド — 深さのある自己開示

`--help` はオプションの一覧を見せるだけ。`man` は理解を与える — 説明、例、関連コマンド (SEE ALSO)、注意事項。この深さが体験を変える。

syslenz のメトリクスも同じであるべきだ:
- NORMAL: 1行の概要 (`--help` 相当)
- DETAILED: 2-3行の解説 + SEE ALSO (`man` 相当)
- EXTRA: 完全な解説 + 診断Tips + コンテキストヒント (教科書相当)

### 2. Python help() — 使いながら学べる自己開示

エピソード: 凄腕プログラマと客先でポートスキャナーを作った。相手は Ruby、こちらは Python。Python が勝った。なぜなら Python の interactive shell では `help(socket)` で全メソッドのドキュメントが読めたから。Ruby にはその機能がなかった。

**教訓: 自己開示するシステムは、しないシステムに勝つ。** ツールから離れずにドキュメントにアクセスできることが、スキルの差を覆す。

syslenz への適用:
- フィールドを見てる時に、その場でヘルプが読める (? キー)
- 関連メトリクスへの SEE ALSO リンク
- 異常値の時だけ表示されるコンテキストヒント

### 3. ノイズ vs シグナル — 600フィールド問題

600フィールドのうち、初心者が見るのは10個。残り590はノイズに見える。しかし:

> 「nr_dirty_threshold がノイズに見えるのは、それが何か知らないからだ。Dirty pages が書き込みストームを起こしている時、この数字が答えになる。」— ハウス (DGE 017)

問題は表示量ではない。**「いつ、何が重要になるか」を教えないこと** が問題だ。

解決策: コンテキスト依存の教育
- 普段は見えない情報が、問題が発生した瞬間に「これを見ろ」と教えてくれる
- 診断結果から関連メトリクスへのジャンプ
- 値が異常な時だけ表示されるコンテキストヒント

## 7つの設計原則

### 1. Progressive Disclosure (段階的開示)
全部を一度に見せない。ユーザーのレベルに合わせて深さを変える。
OFF → NORMAL → DETAILED → EXTRA。

### 2. SEE ALSO (関連メトリクス)
全てのフィールドは孤立していない。MemAvailable を見たら、次に Cached、SwapFree、pgfault を見るべきだと教える。man の SEE ALSO と同じ。

### 3. Contextual Education (コンテキスト依存教育)
値が正常な時と異常な時で、表示する教育コンテンツを変える。異常時にのみ「⚠ メモリが圧迫されています」と表示。

### 4. Diagnostic Deep-Dive (診断から学習へ)
診断結果は終点ではなく、学習の入口。「メモリ不足」という診断から、関連メトリクスの詳細に飛べる。

### 5. Learning Breadcrumbs (学習の道しるべ)
「これを理解したら、次は○○を見てみよう」— ユーザーを次の知識へ導く。

### 6. No Content Truncation (コンテンツ制限なし)
教育コンテンツの長さを UI の都合で切らない。本1章分の量があってもスクロールで全部読める。

### 7. Self-Disclosing System (自己開示するシステム)
syslenz 自体が教科書である。外部ドキュメントを開かなくても、ツール内で全てが学べる。
